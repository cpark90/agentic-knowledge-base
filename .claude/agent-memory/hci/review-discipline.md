# hci 검토 규율 — 2026-09-29~10-02 에 실제로 틀린 것에서 뽑았다

1. **재검토의 첫 단계는 질문지의 `답:` 줄을 다시 읽는 것이다**(옛 채널에서는 항목의 `## 답`). 유저는 답을 고쳐 적는다. 2026-09-30 에 `jev-credentials` 의 답이 "1." 에서 "jev 를 직접 쓰지 않음"으로 바뀌었는데 읽지 않고 반대 방향의 재검토를 냈다. 태깅(`status`)만 보지 말고 본문을 본다.
2. **"참고하라"와 "도입하라"를 갈라 묻는다.** 유저가 외부 사례(jev)를 기준으로 들면 방법론의 참고인지 서비스의 도입인지를 항목의 첫 질문으로 세운다. 가르지 않아 결정·도구·ODD 조건까지 내려갔다가 되돌렸다.
3. **유저의 정의를 받으면 내 틀로 번역하지 않는다.** "서비스 = 에이전트가 쓰는 지식 베이스"를 접점 셋·skill API 로 옮겼다가 정정받았다. 유저 문장을 결정 문장으로 그대로 쓰고, 내 해석은 "hci 의 읽기"로 따로 표시한다.
4. **산발은 제거가 아니라 편입이다**(유저 결정 2026-10-01). 서비스 밖으로 분류해 빼는 안을 내지 않는다.
5. **근사 수치에는 방법과 한계를 같이 적는다.** 토큰 근사(한글 3자/토큰)는 실측 2.35 와 1.7배 달랐고, 정규식 한 벌로 센 "정의문 규칙 36"은 52, "FAIL 태그 44"는 네 목록 합집합 56 이었다. 한 목록만 세고 전수인 것처럼 적지 않는다.
6. **성공 조건에는 단위를 적는다.** "`pct` 36 안팎"은 호출 표현식 수였고 링크의 단위는 호출하는 청크(12)였다.
7. **닫는 순서는 사슬 단위다**(2026-10-03 개정). `result` 가 `re` 로 `task` 를, `task` 가 `source` 로 질문지를 가리킨다. `result` 를 `mark.sh done` 으로 보관한 뒤 질문지를 `closed` 로 고쳐 `harness/user/archive/` 로 옮긴다. 질문지를 지우지 않는다 — `source` 가 실재를 요구하고 `channel_lint` 가 FAIL 한다. 옛 refresh(항목 제거)는 없다.
8. **휘발성 데이터는 보이면 바로 옮긴다.** 다른 세션 스크래치패드의 실험 응답은 `harness/user/` 아래(선례 `harness/user/archive/legacy/inquiries/label-exp-2026-09-30/`)로 복사하고 정식 자리(`kb/vv/run/`)로의 이동을 `task` 에 적는다.
9. **유저가 orchestrator 세션에 직접 지시할 수 있다.** 그 지시는 유효하고 orchestrator 가 `status` 로 알려 온다. 그때 질문지를 사후 기록으로 쓰고(`답:` 에 원문, `closed`) 순서를 적는다.
10. 판정 자격·키는 채널에 적지 않는다.
11. **삭제·통합안의 범위는 참조를 전수로 읽은 뒤 적는다. "문장 정정"과 "규칙 폐지"를 가른다.** 2026-10-06 구조 통합안에서 `kg/composite-kg.ttl` 삭제를 "stable 결정 4개의 문장 정정"이라 적었다. 실행 직전에 전수로 읽으니 결정 넷이 그 파일을 규칙으로 지정하고 있었고(예비 규칙·채택 자리·IRI 꼴), 유저는 범위를 다시 보고 유지(Q67-b)를 골랐다. 결정이 규칙으로 지정한 빈 자리는 잔존물이 아니다. 파일 이름으로 `grep -l` 한 수를 범위로 적지 말고 걸린 줄을 읽는다.
12. **참조는 파일 이름과 함께 문서의 이름(한글 호칭)으로도 찾는다.** 2026-10-06 `docs/decomposition-audit.md`를 지울 때 파일 이름으로만 grep 해 "가리키는 곳은 README뿐"이라 적었다. stable 요구 7건이 "재도출 감사 §3"이라는 이름으로 인용하고 있었고 지운 뒤에야 나왔다(Q70).
