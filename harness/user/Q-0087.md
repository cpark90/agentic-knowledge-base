## Q190. S5를 착수안대로 시작하는가

착수안은 네 단위를 한 번에 하나씩, 단위마다 전후 커밋으로 실행한다.
1. 손 문서 셋을 합친다. 요구 색인 뷰에 이해관계자 열을 더하고 INTENT의 손 목록을 없앤다. 역량 질문 문서는 질의가 없는 8개만 남기고 뷰를 가리킨다. 목적 절은 INTENT 하나로 모은다.
2. 세션 교훈 공간을 닫는다(Q193의 답대로).
3. 코드 추출 범위 공간을 닫고 결정 둘을 개정한다(Q191·Q192의 답대로).
4. 추출 범위를 실행한다(Q191의 답대로). 가장 크고 되돌릴 일이 많아 마지막에 둔다.

어려운 점은 단위 3·4의 크기가 Q191의 답에 달려 있다는 것이다. Q191을 (c)로 답하면 단위 4는 없다.

이미 정해진 것과 현재 상태는 머리 인용 블록에 있다. 기획이 S5에 함께 붙였던 셋(판정 주석의 근사 중복, 설계 공간의 보류와 만료, `//kg:gate_test`의 분할)은 이 착수안 밖이고, S5가 끝난 뒤 따로 올라온다.

- (a) **착수안대로 시작한다.** 손 저작 새 파일은 0이다(Q193을 (b)로 답하면 약 20). 추출물은 단위 1에서 새 0~1개, 재추출 3~5개다. 단위 4는 Q191의 답에 따른다. 권한·방향: 바꾼다
- (b) **시작하지 않는다.** 다음 단계는 interpreter 3단계이고, Q187-a에 따라 외부 수요가 확인될 때까지 기다린다. 권한·방향: 그대로

**권장:** (a) — Q187-a가 정한 순서이고, 손 문서 셋은 이미 낡은 수치를 싣고 있다.

## Q191. 코드 추출 범위를 어디까지 줄이는가 (Q142-a의 해석)

Q142-a는 "결정이 정제하는 함수와 공개 접점만 추출한다"고 정했다. 실측에서 앞의 기준은 구조상 0개다. 결정 `p7-code-links-on-file-composite`(코드 링크의 높이)가 함수에 링크를 달지 않게 하므로, 결정을 가리키는 함수가 생길 수 없다. 그래서 Q142-a는 "공개 접점"을 어떻게 정의하느냐로 결과가 크게 갈린다.
- 이름이 `_`로 시작하지 않는 최상위 정의를 공개 접점으로 보면 669개다(P1).
- 다른 파일이 실제로 import해 쓰는 정의와 CLI `main`을 합치면 175개다(P2).

어려운 점은 줄일수록 Q142-a의 방향("나머지는 모듈 항목 하나")에 가까워지지만, stable 결정 둘의 개정과 검사의 제거가 따른다는 것이다. 함수 본문을 모듈 항목에 합칠 수는 없다. 소스 46개 가운데 34개가 인용 상한 2,856토큰을 넘기 때문이다.

이미 정해진 것과 현재 상태는 머리 인용 블록에 있다. 착수안은 지우는 추출물을 등록부 규약대로 지운다고 적었다. Q142-a의 문구는 "deprecated가 된다"였다. 어느 쪽이든 원문은 소스와 git 이력에 남는다.

- (a) **모듈 항목과 질의 항목만 남긴다.** 86개가 남고 1,038개(약 44.6만 토큰)가 없어진다. 추출물의 토큰 비율은 42.7%에서 약 8%가 된다. 잃는 것은 셋이다. 함수 단위 `uses` 그래프(간선 1,252), 작업 집합의 함수 단위 선택, TIM 판정 4건의 대상 절이다. 판정 4건은 모듈 항목을 가리키게 고친다. 결정 `p7-code-extraction-direction`(코드의 추출 방향)과 `p7-code-links-on-file-composite`(코드 링크의 높이)를 개정한다. 게이트 `extract`의 부분 수 검사와 `code-part-link`는 검사할 대상이 없어져 없앤다. 이것은 검사의 제거이므로 이 답이 그 승인이다. 권한·방향: 바꾼다
- (b) **실제로 쓰이는 접점(P2)만 함수로 남긴다.** 261개가 남고 863개가 없어진다. 복합체 부분 수 규칙(2~9)에 예외를 새로 둬야 한다. 부분이 하나뿐인 모듈 34개와, 부분이 94개인 `kb_lib`가 걸린다. 같은 결정 둘을 개정하고, 함수에 링크를 달지 않는 규칙은 그대로다. 권한·방향: 바꾼다
- (c) **지금처럼 모두 추출한다(Q142-a를 거둔다).** 추출물 수와 토큰은 그대로다. 결정과 게이트는 바뀌지 않고 S5의 단위 4가 없어진다. 권한·방향: 그대로

**권장:** (a) — orchestrator의 추천이다. 기존 규칙에 예외를 더하지 않고 Q142-a의 방향을 실현하는 것은 (a)뿐이다. 없어지는 1,038개를 바깥에서 가리키는 곳은 절 하나뿐이다. interpreter가 덧붙인다. 잃는 함수 단위 `uses` 그래프는 영향 측정 `bazel run //tools:impact`가 쓰지 않는다(impact는 Bazel `rdeps`만 본다). 따라서 영향 측정은 줄지 않는다.

## Q192. `code-projection-range-space`(코드를 단위 지식으로 투영하는 범위를 무엇이 정하는가)를 어느 후보로 닫는가

이 공간은 새 코드 파일이 추출 대상인지를 목록을 고치기 전에 판단할 기준이 없다는 질문을 열었다. 지금 추출 목록은 셋이다. `EXTRACTED_SOURCES` 43개, `EXTRACTED_QUERY_DIRS` 2개, `EXTRACTED_STARLARK` 1개다. 목록 밖의 git 추적 코드는 25개다. `defs/knowledge.bzl`, `defs/tests/` 11개, `harness/scripts/*.sh` 10개, `harness/scripts_test.py`, `kb/ontology/modules.bzl`, `tools/relock.sh`이다. 공간 문서의 수치(42개, 9개)는 낡았다.

어려운 점은 원리를 정하면 판단은 쉬워지지만 원리가 들어맞지 않는 파일이 나올 수 있다는 것이다. 지금 목록의 안팎은 모두 아래 원리 하나로 갈린다.

이미 정해진 것과 현재 상태는 머리 인용 블록에 있다. 이 질문은 무엇을 추출하는가(어느 파일)를 정하고, Q191은 파일 안에서 얼마나 잘게 추출하는가를 정한다.

- (a) **후보 B `p7-extraction-range-by-principle`(원리로 정하는 추출 범위)로 닫는다.** 원리는 "규칙을 강제하거나 질의로 답하는 코드 파일은 추출하고, 빌드 배선과 시험, 하네스 운영 스크립트는 추출하지 않는다"이다. 새 파일은 이 원리로 판정하고, 목록은 그 판정을 적는 자리가 된다. 기존 후보 파일을 확정하므로 새 파일은 없다. 권한·방향: 그대로
- (b) **후보 A `p7-extraction-range-by-list`(목록으로 정하는 추출 범위)로 닫는다.** 지금처럼 새 파일마다 목록을 고칠 때 판단한다. 판단 기준은 문서에 남지 않는다. 권한·방향: 그대로

**권장:** (a) — 공간이 연 질문에 답하는 것은 (a)이고, 지금 목록 안팎의 파일이 모두 그 원리로 갈린다.

## Q193. `session-lesson-place-space`(세션 교훈을 역할 메모리와 작업 메모리 중 어디에 두는가)를 어느 후보로 닫는가

세션 교훈이 지금 세 곳에 나뉘어 있다. interpreter의 역할 메모리 `.claude/agent-memory/interpreter/`에 15개가 있다. 작업 메모리 `kb/dev/memory/`에는 관측 5개가 있고 세션 교훈은 0개다. orchestrator의 교훈은 저장소 밖 Claude 메모리에 있다(파일 20개).

어려운 점은 결정 `p11-lesson-promotion`(교훈의 기록과 승격)이 이미 "역할 메모리에 남긴다"고 정했는데, orchestrator만 역할 메모리를 저장소 밖에 두고 있다는 것이다.

이미 정해진 것과 현재 상태는 머리 인용 블록에 있다. 작업 메모리의 항목은 관측, 곧 덧붙이기만 하는 실행 기록이다(`p0-run-is-an-append-only-memory-chunk`(실행 기록은 kb/vv/run/의 append-only memory 단위 지식이다)).

- (a) **후보 A `p11-session-lessons-in-role-memory`(역할 메모리의 세션 교훈)로 닫는다.** 파일 이동이 없다. orchestrator의 교훈은 지금처럼 저장소 밖에 둔다. 권한·방향: 그대로
- (b) **A로 닫고 orchestrator의 교훈을 저장소의 `.claude/agent-memory/orchestrator/`로 옮긴다.** 새 파일이 약 20개 생기고, 교훈이 git에 들어가 push된다. interpreter가 확인한 사실을 덧붙인다. 저장소 밖 메모리 20개 가운데 11개는 교훈이 아니라 유저의 결정과 선호(`user-` 접두)이고, 1개는 색인이다. 옮기면 그 내용도 원격 저장소에 올라간다. 그래서 (b)를 고르면 교훈만 골라 옮기는 범위를 착수 때 다시 정한다. 권한·방향: 그대로
- (c) **후보 B `p11-session-lessons-in-memory-plane`(작업 메모리의 세션 교훈)로 닫는다.** 작업 메모리의 항목이 관측이라는 결정과 부딪히고, stable 결정 `p11-lesson-promotion`(교훈의 기록과 승격)을 개정해야 한다. 권한·방향: 바꾼다

**권장:** (a) — stable 결정이 이미 역할 메모리를 정했고, 작업 메모리에는 세션 교훈이 없다. orchestrator의 교훈을 저장소로 옮길지는 위치가 아니라 공개 범위의 문제라 이 공간과 따로 다루는 편이 낫다.
