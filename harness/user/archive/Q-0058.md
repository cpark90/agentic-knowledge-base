# interpreter 기획안의 갈림길

> 유저가 Q-0056의 끝에 적은 방향(지식 베이스는 orchestrator와 interpreter 두 에이전트로 서비스된다)에 따라 orchestrator가 기획안을 썼다(result 0198). 본문은 `.scratch/0195/plan.md`(409줄)에 있고 저장소 파일은 바꾸지 않았다. hci가 기획안을 읽었다. 아래는 그 요지와 유저 결정이 필요한 갈림길 아홉, 그리고 1단계 착수 여부다. 답을 받은 뒤 1단계부터 지시한다.

## 기획안의 요지

- **역할.** hci가 지금 하는 일 일곱 가운데 다섯(요청의 해석, 저장소 조회로 직접 답하기, 지시 작성, 되묻기 중계, 결과 검증)은 모든 외부 대상에 공통이고, 둘(질문지, git 관리)은 유저 전용이다. 외부 대상은 유저와 타 프로젝트의 에이전트, 모델 학습·검사 파이프라인(r-030, r-031), 다음 프로젝트(r-002)의 넷이다. 어느 대상에서도 interpreter는 확정 권한을 갖지 않는다.
- **채널.** 바깥 구간(외부 대상과 interpreter 사이)은 대상마다 맞는 매개를 두고 interpreter가 쓰기 요청만 수신함 메시지로 옮기는 안을, 안쪽 구간(interpreter와 orchestrator 사이)은 지금의 채널에 `origin` 필드만 더하는 안을 권장한다. 그러면 단일 작성자 규칙과 메시지 형식, 게이트가 그대로 남는다.
- **매개.** 런타임에 매이지 않는 JSON 형식 넷이다. 확정 지식의 내보내기 묶음, 질의와 응답(응답은 작업 집합이다), 후보 제안, 모델 출력의 검사다. 믿음 정도는 상태와 다른 필드에 싸고, 모델이 낸 확률과도 필드를 나눈다.
- **권한.** 외부 대상의 쓰기는 후보 제안까지다. 기존 결정 넷(`p11-harness-two-channels`, `p11-role-sessions-and-dispatch-models`, `p11-hci-investigates-and-commits`, `p7-dev-roles-and-scopes`)과 요구 하나(r-003), ODD 조건 둘이 개정 대상이다.
- **단계.** 다섯 단계이고 새 파일은 46이다. 1단계 5(역할 이름과 문서), 2단계 3(세션과 채널의 이름), 3단계 16(매개와 내보내기), 4단계 9(모델 출력의 검사), 5단계 13(외부 에이전트의 채널)이다.

## Q121. interpreter를 세션 하나로 두는가, 외부 대상마다 두는가

### 질문
interpreter 세션의 수를 정한다.

### 이미 정해진 것
수신함은 단일 작성자다(`p11-harness-two-channels`). 동시 에이전트의 ODD 한도는 5이고 지금 역할 넷의 합은 4다.

### 현재 상태
hci 세션 하나가 유저 하나를 맡는다.

### 답이 가르는 것
세션 하나면 지금의 채널에 `origin` 필드만 더하면 되고 단일 작성자가 그대로다. 대상마다 세션을 두면 수신함을 대상별로 나누어야 하고 ODD 한도를 넓혀야 한다.

### 선택지
- (a) **세션 하나가 모든 외부 대상을 맡는다.** 대상은 메시지의 `origin`으로 가른다. 읽기 요청은 도구가 답하므로 세션에 섞이는 것은 쓰기 요청과 유저 대화만이다.
- (b) **대상 종류마다 세션 하나를 둔다**(유저용, 에이전트용, 파이프라인용). 세션이 둘 늘어 합이 6이 되므로 ODD 한도를 넓혀야 하고, 수신함을 대상별 하위 디렉토리로 나눈다.
- (c) **유저용은 세션으로 두고, 에이전트와 파이프라인용은 요청마다 띄운다.** 누가 띄우는지를 새로 정해야 하고 카탈로그 역할이 둘로 갈린다.

**권장:** (a). 바꾸는 것이 가장 적고, 외부 에이전트가 실제로 생긴 뒤 부하를 재어 (b)나 (c)로 옮길 수 있다.

답:a

## Q122. 타 프로젝트 에이전트의 런타임을 무엇으로 가정하는가

### 질문
외부 에이전트가 지식 베이스에 닿는 방법의 전제를 정한다.

### 이미 정해진 것
ODD 조건 `cond-network`의 값은 "처음 받아온 뒤 오프라인"이다. 네트워크를 상시 쓰는 설계는 ODD를 먼저 넓혀야 한다.

### 현재 상태
외부 에이전트는 아직 없다.

### 답이 가르는 것
가정이 좁으면 어댑터가 단순하지만 받는 대상이 적다. 가정이 넓으면 서버와 인증이 생기고 ODD가 바뀐다.

### 선택지
- (a) **같은 기계의 Claude Code 세션만 가정한다.** 파일 교환함만으로 충분하다. 다른 프레임워크의 에이전트는 받지 못한다.
- (b) **MCP 클라이언트를 가정하고 표준 입출력(stdio) MCP 서버를 둔다.** Claude Code와 MCP를 쓰는 다른 프레임워크가 함께 붙는다. 네트워크를 쓰지 않으므로 ODD를 바꾸지 않는다. 서버 도구 하나와 그 검사가 생긴다.
- (c) **임의의 HTTP 클라이언트를 가정하고 HTTP 서버를 둔다.** 다른 기계의 대상도 붙는다. ODD 조건을 넓히고 인증과 접근 통제를 새로 정해야 한다.

**권장:** (b). 매개를 JSON 문서로 정해 두면 운반 수단만 바꾸어 뒤에 (c)로 넓힐 수 있고, (b)는 지금의 ODD 안에서 가장 넓은 대상을 받는다.

답:b

## Q123. interpreter의 한글 이름

### 질문
용어집과 카탈로그 라벨에 쓸 한글 이름을 정한다. 산문에서는 지금의 hci와 orchestrator처럼 영문 식별자 `interpreter`를 쓴다.

### 이미 정해진 것
용어집은 표준어가 없으면 서술어로 풀어 쓰라고 정한다. 지금 hci 역할의 한글 라벨은 "유저 소통"이고 orchestrator의 라벨은 음역 "오케스트레이터"다.

### 현재 상태
용어집에 interpreter 행이 없다. "해석기"가 표준 용어인지는 확인하지 못했다.

### 답이 가르는 것
카탈로그 라벨과 용어집 행, AGENTS.md 역할 표의 한글 이름이 정해진다.

### 선택지
- (a) **"외부 소통".** 서술어이고 "유저 소통"과 짜임이 같다. 유저도 외부 대상이므로 뜻이 맞는다.
- (b) **"인터프리터".** 음역이고 "오케스트레이터"가 선례다. 프로그래밍 언어의 해석기와 같은 말이라 혼동이 생길 수 있다.
- (c) **"통역".** 관용어이지만 비유이므로 문장 규칙(비유는 실제 동작으로 바꾼다)과 어긋난다.

**권장:** (a). 용어집의 규칙과 기존 라벨의 짜임을 함께 따른다.

답:b, interpreter는 프로그래밍 언어의 해석기에서 차용한 용어임. 그와 유사한 역할을 할 예정임.

## Q124. 카탈로그의 role-hci를 어떻게 하는가

### 질문
역할 카탈로그(`kg/catalog-kg.ttl`)에서 hci 역할을 어떻게 바꾸는지 정한다.

### 이미 정해진 것
역할과 권한의 형식 원본은 카탈로그이고, 지식 항목의 생성자(`generated.by`)는 카탈로그의 역할로 검사한다.

### 현재 상태
`generated.by`가 `hci/…`인 지식 항목이 약 203개다(orchestrator의 정규식 집계이며 hci는 다시 세지 않았다). 지난 사실이므로 고치지 않는다.

### 답이 가르는 것
옛 이름을 남기지 않으면 그 203개가 "역할 없는 생성자"가 되어 검사에서 빠진다.

### 선택지
- (a) **`role-interpreter`로 이름을 바꾸고 옛 이름 "hci"를 숨은 라벨(`skos:hiddenLabel`)로 남긴다.** 생성자 검사가 숨은 라벨도 읽도록 고친다. 역할은 넷으로 남는다.
- (b) **둘을 함께 둔다.** interpreter가 상위 역할이고 hci가 유저 대상 하위 역할이다. 하위 역할을 나타낼 술어가 없어 새 개념 파일이 생기고, 동시 에이전트 합이 5가 되어 ODD 한도에 닿는다.
- (c) **이름만 바꾸고 옛 이름을 남기지 않는다.** 검사가 약해진다.

**권장:** (a).

답:b

## Q125. 외부 대상의 쓰기 상한

### 질문
타 프로젝트의 에이전트와 파이프라인이 지식 베이스에 무엇까지 쓸 수 있는지 정한다. 확정 권한에 걸리는 질문이다.

### 이미 정해진 것
확정은 유저 또는 위임된 에이전트의 확인으로 한다(`p10-candidate-and-confirmed-link`). 참조 프로파일의 claim 역할은 "제안만" 할 수 있다.

### 현재 상태
외부 대상의 쓰기 경로가 없다.

### 답이 가르는 것
읽기만 허용하면 외부 지식을 받지 못한다. 후보 제안까지면 외부 지식이 증거 종류 `proposal`로 들어오고 확정은 지금의 경로를 탄다. 확정 위임까지면 외부 에이전트가 이 프로젝트의 확정 지식을 바꾼다.

### 선택지
- (a) **읽기만.**
- (b) **후보 제안까지.** 제안의 형식 검사와 처리 경로가 생긴다.
- (c) **등록된 외부 에이전트에 일부 지식 종류의 확정을 위임한다.** 확정 결정의 개정과 위임 범위를 적는 새 결정이 필요하다.

**권장:** (b). 확정 권한을 바꾸지 않고 외부 지식을 받는 가장 높은 상한이다.

답:b

## Q126. 외부에서 온 후보를 누가 확정하는가

### 질문
외부 제안으로 들어온 후보의 확정 주체를 정한다. 확정 권한에 걸리는 질문이다.

### 이미 정해진 것
지금 후보의 확정은 유저가 질문지로 한다. orchestrator는 유저가 위임한 범위에서만 확정한다.

### 현재 상태
외부 제안이 아직 없어 양과 질을 모른다.

### 답이 가르는 것
유저가 확정하면 모든 외부 출처의 확정에 유저의 답이 근거로 남지만 질문지가 늘어난다. orchestrator에 위임하면 유저의 부담이 줄지만 위임 범위를 적는 결정이 하나 생긴다.

### 선택지
- (a) **처음에는 항상 유저가 질문지로 확정한다.** 관측이 쌓이면 위임을 다시 묻는다.
- (b) **유저가 미리 정한 범위 안에서는 orchestrator가 확정하고 결과만 보고한다.**

**권장:** (a). 외부 제안의 실제 양과 질을 보기 전에는 위임 범위를 정할 근거가 없다.

답:b

## Q127. 타 프로젝트의 에이전트에 지식 항목 본문을 주는가

### 질문
질의의 응답에 지식 항목 본문을 담아 외부 에이전트에 줄 수 있는지 정한다.

### 이미 정해진 것
요구 r-003은 "지식 항목은 프로젝트를 넘지 않는다"이고, 그 근거는 ODD가 다르면 가정의 판정이 성립하지 않는다는 것이다. 요구 r-002는 다음 프로젝트에 어휘와 공리, ODD 코어, 교훈만 넘긴다. 서비스의 접점은 작업 집합이다(`p0-service-is-a-three-layer-wiki`).

### 현재 상태
r-003은 응답으로 보여 주는 것이 "넘는 것"인지를 가르지 않는다.

### 답이 가르는 것
본문을 주지 않으면 질의와 응답이 사실상 막힌다. 주되 투영으로 한정하면 r-003의 뜻이 지켜지면서 질의가 쓸모를 갖는다. r-003을 개정하면 받는 쪽이 저장도 한다.

### 선택지
- (a) **투영으로 준다.** 응답에 이 프로젝트의 ODD 조건을 붙이고, 요청자의 ODD 값이 다르면 `odd_mismatch` 표시를 더한다. 받는 쪽이 자기 지식 항목으로 저장하지 않는다는 조건을 매개에 적는다. r-003에 "투영은 경계를 넘는 것이 아니다"를 덧붙인다.
- (b) **r-002의 넷(어휘, 공리, ODD 코어, 교훈)만 준다.** r-003을 고치지 않지만 질의가 막힌다.
- (c) **r-003을 개정하여 확정 지식 항목은 ODD 조건 묶음과 함께라면 넘을 수 있게 한다.** stable 요구의 개정이다.

**권장:** (a).

답:a

## Q128. 채널 후보의 선택

### 질문
바깥 구간(외부 대상과 interpreter 사이)과 안쪽 구간(interpreter와 orchestrator 사이)의 채널 방식을 정한다.

### 이미 정해진 것
수신함은 단일 작성자다. 채널 메시지는 git 밖에 둔다.

### 현재 상태
바깥 구간은 질문지(유저만), 안쪽 구간은 수신함 메시지다.

### 답이 가르는 것
수신함을 바깥까지 넓히면 코드가 가장 적지만 단일 작성자 규칙이 깨지고 다른 기계의 대상이 닿지 못한다. 매개마다 번역하면 어댑터와 MCP 서버가 생기지만 규칙과 메시지 형식이 그대로 남는다.

### 선택지
- (a) **바깥은 매개별 번역, 안쪽은 지금 채널에 `origin` 필드.** 유저는 질문지를, 에이전트는 MCP 서버와 파일 교환함을, 파이프라인은 내보내기 디렉토리와 검사 요청 파일을 쓴다. interpreter가 쓰기 요청만 수신함 메시지로 옮긴다.
- (b) **바깥도 수신함 확장, 안쪽은 지금 채널에 `origin` 필드.** 외부 대상이 `send.sh`로 수신함에 직접 쓴다. 단일 작성자 규칙을 개정한다.
- (c) **(a)에 git 패치 제안 큐를 더한다.** 지식 항목 초안은 git 패치로, 질의와 링크 제안은 매개로 받는다.

**권장:** (a). 제안 큐는 (a)가 자리 잡은 뒤 초안 제안이 많아지면 더한다.

답:a

## Q129. 메시지 type에 `proposal`을 더하는가

### 질문
수신함 메시지의 type 어휘(지금 일곱)에 외부 제안을 담는 `proposal`을 더하는지 정한다.

### 이미 정해진 것
`knowledge` type은 유저가 확인한 사실을 승격할 때 쓴다.

### 현재 상태
외부 제안을 담을 type이 없다.

### 답이 가르는 것
`proposal`을 더하면 승격(`knowledge`)과 후보 등록(`proposal`)이 type으로 갈린다. `knowledge`에 증거 종류 줄을 붙여 쓰면 새 어휘는 없지만 orchestrator가 본문으로 둘을 갈라야 하고, 후보가 확정으로 승격될 위험이 생긴다.

### 선택지
- (a) **`proposal`을 더한다.** interpreter에서 orchestrator로 가며 본문은 대상과 증거, 이유다. type 어휘와 게이트, `send.sh`가 바뀐다.
- (b) **`knowledge`에 증거 종류 줄을 붙여 쓴다.**

## Q130. 1단계를 바로 시작하는가

### 질문
위 답을 받은 뒤 1단계(역할 이름과 문서)를 바로 지시하는지 정한다.

### 이미 정해진 것
새 파일은 만들기 전에 묻는다(Q66). 1단계의 새 파일은 다섯이다. 결정 `p11-interpreter-generalizes-hci`(네 파일)와 요구 r-033(외부 대상은 interpreter를 거쳐 지식 베이스와 소통한다)이다.

### 현재 상태
hci 세션은 그대로 돌고, 1단계는 카탈로그 역할의 개명과 문서 변경, 결정 넷의 개정만 한다. 2단계부터 세션과 채널의 이름이 바뀐다.

### 답이 가르는 것
바로 시작하면 1단계가 검토 후속 지시들의 뒤에 줄을 선다. 미루면 기획안을 다시 다듬을 시간이 생기지만 방향이 정해진 채 실행만 늦어진다.

### 선택지
- (a) **답을 받은 뒤 1단계를 바로 지시한다.** 새 파일 다섯을 함께 승인한다. 2단계 이후는 단계마다 다시 묻는다.
- (b) **기획안을 다듬은 뒤 시작한다.** 다듬을 점을 `답:` 뒤에 적어 주면 된다.

**권장:** (a).
