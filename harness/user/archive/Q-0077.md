# 표준 OWL 도구용 import 대응표의 자리

> **이미 정해진 것**
> - Q176-a(Q-0076): 표준 OWL 도구가 import를 풀 수 있게 대응표 `catalog-v001.xml`을 생성하고, 모듈 파일은 고치지 않는다. 그때 승인한
>   새 생성 파일은 하나였다.
> - 결정 `p2-ontology-module-structure`(온톨로지의 모듈 구조): 모듈은 디렉토리이고 기존 모듈 파일은 고치지 않는다.
> - 결정 `pe-generated-outputs-stay-in-bazel-out`(생성물은 bazel-out에 둔다): 생성물은 `bazel-out`에만 둔다. 소스 트리에 두는 예외는 드리프트
>   테스트를 갖춘 셋(생성 BUILD, skill, 규범 문서)뿐이다.
> - Q175-a(Q-0076): ROBOT은 들이지 않는다. 표준 도구 확인은 저장소 밖에서 한 번 실행한다.
>
> **현재 상태** (2026-11-27, orchestrator가 재고 interpreter가 확인)
> - **Q176의 선택지 (a)는 잘못된 전제 위에 있었다.** XML Catalog는 IRI 하나를 파일 하나에 대응시키고, 같은 IRI 항목이 여럿이면 첫 항목만
>   쓴다. 그런데 모듈 14개 가운데 9개가 파일 여러 개로 되어 있다(defect 17, trace 13, development 10, harness 6, layer·knowledge-item·condition 4,
>   defect-rules 3, state 2). 대응표 하나만으로는 이 9개 모듈의 내용이 다 보이지 않는다. 그래서 모듈마다 파일 하나로 합친 **합본**이 어딘가에
>   있어야 한다. interpreter는 Q-0076을 쓸 때 이 점을 확인하지 않았다.
> - 모듈을 내보내는 빌드 규칙(`defs/kb.bzl`의 `kb_ontology_module`)은 원본 파일을 그대로 내보낼 뿐 합본을 만들지 않는다.
> - 이 머신에는 Java 21이 있고 ROBOT과 Protégé는 없다. 표준 도구 확인은 저장소 밖에서 OWL API 기반 도구를 한 번 내려받아 실행할 수 있다.

## Q177. 모듈 합본과 대응표를 어디에 둘 것인가

### 질문
표준 OWL 도구가 import 14개를 모두 풀려면 대응표와 함께 모듈 합본 14개가 필요하다. 합본은 생성기가 모듈의 파일들을 합치고 머리에
`<모듈 IRI> a owl:Ontology`를 붙여 만든다. 그래서 어느 안이든 모듈 파일은 고치지 않는다. 남은 문제는 대응표와 합본을 소스 트리에 저장할지
빌드 산출물(`bazel-bin/`)에만 둘지다. 어려운 점은, 합본을 트리에 두면 온톨로지 내용이 두 벌이 되고, 산출물에만 두면 표준 도구로 열기 전에
`bazel build`가 필요하다는 것이다.

### 답이 가르는 것
소스 트리에 새로 저장하는 파일 수, 결정 `pe-generated-outputs-stay-in-bazel-out`(생성물은 bazel-out에 둔다)의 예외 표에 행이 더해지는지,
드리프트 검사를 두는지, 표준 도구를 쓰기 전에 빌드가 필요한지가 갈린다.

### 선택지
- (a) **대응표는 트리에 저장하고 합본은 `bazel-bin/`에 둔다.** 저장한 `kb/ontology/catalog-v001.xml`이 `bazel-bin/` 아래의 합본을 가리킨다.
  비용은 저장 파일 1, 드리프트 검사 1, 결정의 예외 표에 행 1이다. 그래도 합본은 빌드 뒤에만 있으므로, 새로 클론한 저장소에서는 대응표가 없는
  파일을 가리킨다. 권한·방향: 바꾼다(생성물 예외 추가)
- (b) **합본 14개와 대응표를 모두 트리에 저장한다.** 빌드 없이 표준 도구로 바로 열린다. 비용은 저장 파일 15와 드리프트 검사 1~2다. 온톨로지 내용이
  트리에 두 벌 생기고, 모듈 파일을 고칠 때마다 diff가 두 배가 된다. 결정의 예외 표에도 행이 더해진다. 권한·방향: 바꾼다(생성물 예외 추가)
- (c) **대응표와 합본을 모두 `bazel-bin/`에 둔다.** 빌드 타깃 하나가 `bazel-bin/kb/ontology/` 아래 한 디렉토리에 대응표, 합본 14개,
  `project-ontology.ttl` 사본을 만들고, 표준 도구는 그 사본을 연다. 비용은 저장 파일 0, 드리프트 검사 0이고, 결정의 예외 표도 그대로다. 열기
  전에 `bazel build`가 필요한 것은 (a)와 같다. Q176-a의 "트리에 저장한다"는 부분만 바뀐다. 권한·방향: 그대로
- (d) **만들지 않고 알려진 한계로 적는다.** Q176-c로 돌아간다. 결정 `p2-ontology-module-structure`(온톨로지의 모듈 구조)의 근거에 "표준 도구에서는
  import가 풀리지 않는다"를 적는다. 비용은 없고, smartbelley_vnv 같은 의존 저장소도 표준 도구로는 코어를 열지 못한다. 권한·방향: 그대로

**권장:** (c) — orchestrator와 interpreter의 추천이 같다. (a)에서도 합본은 빌드 뒤에만 있으므로, 대응표를 트리에 둬서 얻는 이점("빌드 없이 읽힌다")이
없다. (c)는 새 저장 파일과 검사를 하나도 더하지 않고, 생성물 결정을 예외 없이 지킨다. 어느 안이든 표준 도구로 실제로 여는 확인은 저장소 밖에서
한 번 실행한다.
