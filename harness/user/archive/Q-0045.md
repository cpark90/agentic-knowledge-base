# 확률화의 첫 단계와 변수 출발 결함

> orchestrator가 질문 둘을 올렸다. 0164는 Q87-b(KB 자체의 확률화)의 첫 단계이고, 0163은 Q85-a (4)(D6)를 수행하다 막힌 자리다.
>
> **이미 정해진 것**
> - Q87 (a)·(b): 확정 KB 위에 확률 모델을 세우고 KB 자체도 확률화한다. Q88: 확률이 표현하는 것은 링크의 믿음 정도 · 결정 후보의 선택 확률 · 질의 답의 분포다.

> - 노트 9.2와 `p9-evidence-ledger`가 확률을 기각한 이유는 "보정할 빈도 데이터가 없다"였다.
>
> **현재 상태 (orchestrator 실측 2026-10-22)**
> - **재료가 한쪽으로 쏠려 있다.** 증거 1,212건은 전부 지지(+)다. 반박(−)은 설계 공간의 배제 근거 5건뿐이다. 증거 종류 7개 가운데 4개(동시 편집·공동 커버·임베딩·세션 읽음)는 실물이 0이다. 사람 정답 라벨은 유저 재판정 10건이 전부이고, 판정자 확신도(0.93~0.97)는 과신이다.

> - 확신도 어휘(judge-threshold·judge-calibration 온톨로지, 확신도 [0,1], 임계 0.9/0.5, 구간 표본 하한 20)는 살아 있다. 원 결정은 deprecated지만 보정 틀의 원형으로 다시 쓸 수 있다.
> - (b)를 끝까지 가면 다섯 단계다. 요구(r-011·r-016) → 증거·가능성 결정 → 상태·확정 결정 → 온톨로지(링크 상태 재정의) → 게이트·도구 개정. stable 결정 최소 6개를 대체한다.

## Q90. r-011을 어떻게 다시 쓰는가

| | (a) 확정 + 믿음 정도 병기 | (b) 확정을 임계로 대체 | (c) 재료 먼저 |
|---|---|---|---|
| r-011 새 문장 | "근거 없는 할당은 불가능해야 한다"를 유지한다. "근거"에 증거 기록과 보정된 믿음 정도를 더한다. 믿음 정도는 상태를 바꾸지 않고 함께 적힌다 | "체계는 보정된 믿음 정도가 임계를 넘지 않은 후보를 확정하지 않아야 한다" | 지금 문장 유지. 아래 선행 조건이 차면 (a)·(b)를 다시 묻는다 |
| 이산 상태 | 확정 권한으로 남는다. 믿음 정도는 덧붙는 값이다 | 임계 구간의 요약이 된다 | 남는다 |
| 32 결정 재판정 | "근거"의 범위만 넓어진다. 대부분 유지 | 전부 다시 판정 | 0 |
| 대체 규모 | 2(evidence-ledger의 "합산 금지", feasible-set의 "확률 미채택"의 범위를 좁힌다) | 다섯 단계 전부, stable 최소 6 | 0 |
| 궁극 목적 끝 문장 | 그대로 | "확정의 권한은 보정된 믿음 정도와 KB의 규칙이 함께 진다"로 고친다 | 그대로 |
| 재료 쏠림 | 병기라서 값이 고르게 나와도 해가 없다. 보정은 표본이 찬 뒤 | 보정 없이 임계가 서면 9.2의 결함이 그대로 남는다 | 정면으로 다룬다 |

- (a) **확정 + 믿음 정도 병기.** 지금 할 일은 셋이다. r-011 개정 초안(draft)을 쓴다. `p9-evidence-ledger`·`p9-possibility-as-feasible-set`의 범위를 "확정의 표현"으로 좁히는 대체 결정 둘을 둔다. Q91의 선행 조건을 설계 공간 하나("믿음 정도의 계산과 보정")로 연다. 새 파일은 결정 2×3 + 공간 1 + 후보 결정 n×3이다. 만들기 전에 수를 다시 알린다.
- (b) **확정 = 임계 통과.** 다섯 단계를 순서대로 하고 단계마다 묻는다.
- (c) **재료를 먼저 채운다.** r-011은 유지하고 Q91의 선행 조건을 지시로 수행한다. 표본 하한에 닿으면 (a)·(b)를 다시 묻는다.

**권장:** (a) — orchestrator의 추천이고 hci도 같다. 유저가 고른 (a)·(b)가 함께 서는 가장 작은 꼴이 "확정 권한은 이산, 믿음 정도는 병기"다. `r-032`의 "가질 수 있어야 한다"와도 맞는다. (b)는 반박 5건 · 사람 라벨 10건으로는 임계를 보정할 수 없어 지금 서지 못한다. (a)는 Q91의 재료가 차는 대로 (b)로 옮겨 갈 길을 연다. 곧 (b)를 버리는 것이 아니라 (a) → (b)의 순서다.

## Q92. 공간 넷의 변수 출발(D6)을 어떻게 고치는가

Q85-a (4)는 공간 넷(candidate-container · layer-scope · requirement-layer · temporal-identity)의 변수 출발을 "출발 결정이 정제하는 요구"로 옮기라고 했다. 그런데 옮길 요구가 전부 다른 공간의 변수로 이미 쓰이고 있다. 변수는 (출발 × 링크 종류) 하나가 공간 파일 하나라, 게이트가 중복을 거부한다. 요구 하나를 여러 결정이 정제하므로(r-011만 32) 이 규칙과 "출발을 요구로"가 맞물려 자리가 없다. 지금 넷 다 게이트는 통과하지만, 확정 후보가 head 링크를 가질 수 없다(concrete → concrete). candidate-container는 resolved인데 A 결론에 head 링크가 없다.

- (a) **출발을 abstract 결정 청크로 둔다.** 출발 결정 복합체마다 abstract 청크 하나(결정 변수 선언)를 더해 출발로 삼는다. 후보 logical·확정 concrete가 그것을 정제하고, 그 abstract는 기존 요구를 정제한다. 새 파일 3~4개다. stable `p6-plane-level-occupancy`가 decision abstract를 "결정 변수 선언"으로 이미 정했다. 저장소의 첫 abstract 결정이 된다.
- (b) **변수 키에 질문을 더해 같은 요구에서 여러 공간을 허용한다.** 새 파일 0이다. 중복 거부 규칙을 넓히는 검사 약화(유저 승인)이고 "변수 하나 = 파일 하나"의 뜻이 흐려진다.
- (c) **D6을 열린 결함으로 남긴다.**

**권장:** (a) — orchestrator의 추천이고 hci도 같다. stable 결정이 정해 둔 빈 칸(decision abstract)이 바로 공간의 변수이고, 검사를 약화하지 않는다.

답:a
