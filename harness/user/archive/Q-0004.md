# 규약과 실물의 어긋남 넷 — 어느 쪽을 원본으로 맞출 것인가

> orchestrator의 확인 요청(메시지 0006)을 질문지로 옮긴 것이다. 통일 기획 2단계에서 orchestrator는 원본 결정이 없던 규약 116개에
> 원본 결정을 달았다. 기존 결정에 링크하거나 새 결정 27개를 저작했다. 그 과정에서 규범 문서와 실물이 어긋나는 자리 넷이 드러났다.
> 각 자리는 해당 결정 근거의 `미확정:`에 적혀 있다.
>
> **이미 정해진 것**
> - shape·게이트 검사의 약화는 유저 승인 사항이다(`AGENTS.md` 황금률 1).
> - `requirement`·`decision`의 stable 전이와 stable 결정의 대체는 유저 승인 사항이다.
> - 규약 각각의 원본은 결정이다(통일 기획 2단계, 2026-10-03).
>
> **현재 상태 (hci 실측 2026-10-03)**
> - `bazel test //...`는 76/76 PASS다(orchestrator 보고). Q5~Q7의 어긋남을 판정하는 게이트는 없고 리뷰에서만 드러난다.
> - 넷 모두 orchestrator의 진술을 저장소에서 확인했다. 줄 번호와 값은 각 질문에 적었다.

## Q5. Bazel 패키지 규약 셋의 위반을 어느 쪽에 맞출 것인가

`STYLEGUIDE.md` §6은 다음 셋을 [지킴]으로 적는다. 실물은 셋 다 어긋난다.

| 규약 | 실물 |
|---|---|
| 게이트는 매크로로만 선언한다. `py_test`를 직접 쓰지 않는다 | `BUILD.bazel:79` `//:build_drift_test`가 `py_test`를 직접 쓴다 |
| filegroup 이름은 디렉토리 이름이다 | `gen_build`가 생성하는 청크 패키지의 filegroup 이름이 `bodies`다. `name = "bodies"`인 BUILD는 55개다 |
| glob은 한 계층이다 | `kb/dev/decision/BUILD.bazel`이 `glob(["**/*.md"])`를 쓴다 |

orchestrator는 "생성 BUILD 67개가 바뀐다"고 적었다. hci가 센 값은 `bodies` filegroup 55개, `gen_build` 언급 74개다. 세는 기준이 달라
셋 다 정확한 수가 아니다. 재생성 대상의 수는 developer가 실행에서 확정한다.

- (a) **코드를 규약에 맞춘다.** developer가 `gen_build`와 최상위 `BUILD.bazel`을 고치고 생성 BUILD를 전부 재생성한다. 규약은 그대로다.
  비용은 생성기 수정, 수십 개 BUILD의 재생성, 이름이 `bodies`인 타깃을 참조하는 곳의 수정이다.
- (b) **규약을 실물에 맞춰 좁힌다.** [지킴] 셋의 문장이 실물을 허용하게 바뀐다. 이것은 검사 약화라 이 답이 승인이 된다. 비용은 문서와
  결정의 문장 수정뿐이다.
- (c) **셋을 따로 정한다.** 항목마다 (a)·(b)를 아래에 적는다.

**권장:** (a) — orchestrator의 추천이다. 규약은 2026-09-01부터 있었고 어긋남은 생성기 쪽의 누락이다.

답:(a)

## Q6. 생성 문서의 입력 접기 경계를 어느 쪽에 맞출 것인가

`STYLEGUIDE.md:280`은 "입력 파일이 일곱을 **넘으면**" 접는다고 적는다. 그러면 여덟 개부터 접는다. 코드 `tools/kb_lib.py:1556`의
`GENDOC_INPUT_INLINE_MAX = 6`은 일곱 개부터 접는다. 입력이 정확히 일곱 개인 생성 문서에서만 둘이 갈린다.

- (a) **문서를 코드에 맞춘다.** 문장을 "일곱 이상"으로 고친다. 비용은 문장 하나다. 생성물은 바뀌지 않는다.
- (b) **코드를 문서에 맞춘다.** 상수를 7로 고친다. 비용은 상수 하나다. 입력이 일곱 개인 생성 문서의 머리 모양이 바뀐다.

**권장:** (a) — orchestrator의 추천이다. 코드는 게이트 `gendoc`과 함께 실측으로 굳은 쪽이다.

답:(a)

## Q7. 면제 추가는 누가 승인하는가

`STYLEGUIDE.md` §7과 `docs/waivers.md`는 면제 추가를 검사 약화로 보고, 검사 약화는 유저 승인 사항이라 적는다. 실물은
`docs/waivers.md` 면제 표 여섯 행의 판정자가 전부 orchestrator다(10~15행, 2026-09-12~10-01).

- (a) **면제 추가도 유저 승인이다.** 규약이 그대로다. 기존 여섯 행은 사후 승인을 받는다. 앞으로 면제 행마다 질문지가 하나씩 생긴다.
- (b) **면제는 orchestrator가 판정하고 선언으로 공개한다.** 약화는 shape·게이트 코드의 변경만이다. 면제를 약화에서 빼는 문장이 규약에
  들어가고, 기존 여섯 행은 규약에 맞게 된다. 비용은 유저가 면제를 사전에 막지 못하는 것이다. 사후에는 `docs/waivers.md`에서 보인다.

**권장:** (b) — orchestrator의 추천이다. 면제는 이미 선언으로 공개되고 판정자와 사유가 기록된다. 행마다 유저 승인을 받으면 흐름이 막힌다.

답:(b)

## Q8. stable 결정 `p0-run-as-observation`을 대체할 것인가

이 결정은 stable이고 결론(`kb/dev/decision/p0-run-as-observation/conclusion.md:19`)이 실행을 `run-kg`에 저장한다고 적는다.
2026-09-19부터 실행 기록은 `kb/vv/run/`의 `memory` 청크다(`docs/rules.md` 개체 IRI 표).

- (a) **새 결정으로 대체한다.** 새 결정이 `supersedes`로 잇고 옛 결정은 deprecated가 된다. 새 결정의 stable 전이는 다시 유저 승인을
  받는다. 비용은 결정 하나의 저작과 승인 1회다.
- (b) **그대로 둔다.** 차이는 `p0-entity-iri-forms`의 근거가 적는 것으로 둔다. 비용은 stable 결정이 실물과 다른 문장을 계속 갖는 것이다.
  3단계 투영이 그 결정에서 문서를 만들면 틀린 문장이 나온다.

**권장:** (a) — orchestrator의 추천이다. 통일 기획 3단계는 결정에서 문서를 생성하므로 stable 결정의 문장이 실물과 같아야 한다.

답:(a)
