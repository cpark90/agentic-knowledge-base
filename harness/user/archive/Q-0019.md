# stable 케이스 셋의 생성 케이스 대체와 중복 케이스 하나

> orchestrator의 확인 요청(메시지 0061)을 질문지로 옮긴 것이다. 수기 케이스를 0으로 만들려면(Q27-a) stable 케이스 셋을 생성 케이스로
> 바꿔야 한다. 원래 stable 청크를 지우고 생성 케이스로 대체하는 것은 stable 변경이므로 승인을 묻는다.
>
> **이미 정해진 것**
> - Q27-a: 케이스 생성기를 쓰고 수기 케이스 0을 지킨다. Q29-a: 비표본 판정은 검증기 단에 둔다.
> - stable 청크의 본문 변경·삭제는 유저 승인 사항이다.
> - 청크 단위는 42줄이 아니라 토큰이다(`p1-chunk-unit-is-tokens`, 2026-10-01).
>
> **현재 상태 (orchestrator 실측 2026-10-04)**
> - 표본 케이스 13 가운데 10은 logical 시나리오로 생성기에서 다시 만들었다. 10 모두 원래 케이스와 판정 내용(`files`·명령·`expect`)이 같다.
>   그 가운데 draft 9는 이미 생성 케이스로 바꿨다. 드리프트 게이트 `case-drift`에 등록하는 중이다.
> - 생성기가 `derivesFrom` 링크를 옮기지 못하는 결함을 developer가 고치는 중이다. 고친 뒤에는 생성 케이스가 원래 링크를 지킨다.

## Q42. stable 케이스 셋을 생성 케이스로 대체하는 것을 승인하는가

| 케이스 | 생성 방법 |
|---|---|
| `foreign-vocabulary-rejected` | 생성 후보가 준비됐다. 시나리오는 저장소에 있다 |
| `chunk-42-lines` | 커밋된 고정물을 명령이 가리켜 지금 생성할 수 있다 |
| `dispatch-workset-budget` | 예산 변수(`values: [200], reject: [10]`)와 요인 `agt:worksetBudgetOverrun` 주입으로 원래 케이스가 그대로 나온다 |

- (a) **셋 모두 승인한다.** 수기 케이스가 0이 되고, `case-drift`의 `all_generated`(트리의 모든 케이스가 생성물)를 켤 수 있다. 판정 내용은 같다.
- (b) **하나씩 승인한다.** 승인할 케이스 이름을 아래에 적는다. 남은 것은 수기 케이스로 남는다.
- (c) **승인하지 않는다.** 셋은 수기 케이스로 남고 Q27-a의 "수기 케이스 0"이 서지 않는다.

**권장:** (a) — orchestrator의 추천이다. 판정 내용은 그대로이고 원본만 손 케이스에서 생성 입력으로 옮긴다.

답:(a)

## Q43. 같은 판정을 하는 케이스 둘 가운데 무엇을 남길 것인가

`token-budget`(draft)은 첫 명령과 기준이 `chunk-42-lines`(stable)와 같아 같은 기준을 두 번 잰다.

- (a) **`token-budget`을 지우고 `chunk-42-lines`의 시나리오 하나로 둔다.** orchestrator의 안이다. stable 청크는 그대로 두고 draft를 지운다.
- (b) **둘 다 남긴다.** 같은 기준을 두 번 잰다.
- (c) **`chunk-42-lines`를 지우고 `token-budget`을 남긴다.** hci가 더한 안이다. 청크 단위는 2026-10-01에 42줄에서 토큰으로 바뀌었다. 남는
  케이스의 이름이 지금 단위를 가리킨다. 비용은 stable 청크의 삭제이고, 이 답이 그 승인이 된다.

**권장:** (c) — 두 케이스가 같은 판정을 한다면 낡은 단위 이름이 아니라 지금 단위 이름이 남는 편이 낫다. 이름이 판정 대상을 잘못 안내하지 않는다.
다만 `chunk-42-lines`의 명령이 실제로 무엇을 재는지(줄 수인지 토큰인지)는 orchestrator가 확인한 뒤 반영한다.

답:(c)
