# interpreter 1단계의 결과와 2단계 착수

> orchestrator가 interpreter 1단계(지시 0203, Q121~Q133의 답 반영)를 마쳤다(result 0225). hci가 `bazel test //...`로 확인했고, 새 결정과 요구, 카탈로그의 두 역할, 용어집 행, CLAUDE.md 9항, hci 지침의 머리를 직접 보았다. Q130-a는 "2단계 이후는 단계마다 다시 묻는다"고 정했으므로 2단계 착수를 묻는다. 유저의 답으로 바뀐 단계표도 함께 올린다.

## 1단계에서 된 것
- 요구 r-033(외부 대상은 인터프리터를 거쳐서만 지식 베이스와 소통한다)과 그 검증 목표·합격 기준이 생겼다. 모두 stable이다.
- 결정 `p11-interpreter-generalizes-hci`(네 파일, stable)가 Q121~Q129의 답을 인터프리터의 설계로 적는다. 매개 형식과 MCP 세부, 위임 범위, r-003 재서술, type `proposal`은 뒤 단계의 결정이 정한다고 범위로 적었다.
- 카탈로그에 `role-interpreter`(라벨 "인터프리터")가 생기고, `role-hci`는 그 하위 역할이 됐다(새 술어 `agt:subRoleOf`). 동시 에이전트 합은 4로 한도 5 이하다. 하위 역할은 상위 역할의 세션이 맡으므로 0으로 센다.
- 결정 넷(`p7-dev-roles-and-scopes`, `p11-harness-two-channels`, `p11-role-sessions-and-dispatch-models`, `p11-hci-investigates-and-commits`)을 개정했고 재검증은 모두 유지다.
- 용어집에 "인터프리터" 행(유저 설명 원문 포함), harness/README.md의 역할 절, hci 지침의 머리 한 줄, CLAUDE.md 9항, AGENTS.md가 바뀌었다. 새 파일은 승인된 여덟과 같고 추출물은 0개다.
- hci 세션과 스크립트, 채널 디렉토리, channel_lint의 역할 어휘는 바뀌지 않았다.

## Q143. 2단계(세션과 채널의 이름)를 시작하는가

### 질문
hci 세션과 채널의 이름을 interpreter로 옮기는 2단계를 시작하는지, 그리고 hci 지침과 기동 스크립트를 어떻게 남기는지 정한다.

### 이미 정해진 것
- Q121-a: 세션은 하나다. Q124-b: 카탈로그에 interpreter 상위 역할과 hci 하위 역할을 함께 둔다.
- Q130-a: 2단계 이후는 단계마다 다시 묻는다. 새 파일은 만들기 전에 묻는다(Q66).

### 현재 상태
1단계가 끝났다. 2단계의 새 파일은 셋이다. `harness/agents/interpreter.md`(hci 지침을 옮기고 공통 몫, 유저 전용 몫, 대상별 몫의 절로 나눈다), `harness/scripts/run-interpreter.sh`, `.claude/agent-memory/interpreter/`(hci 역할 메모리를 옮긴다. 옮기는 일은 hci가 맡는다)다. 채널 디렉토리 `to_hci/`는 `to_interpreter/`로 옮기고, 스크립트의 역할 어휘와 channel_lint, 카탈로그의 `chan-to-hci`, 결정 `p11-harness-two-channels`의 규약 "to_orchestrator에는 hci만"을 고친다. 기획안은 `hci.md`와 `run-hci.sh`를 지우기로 했으나, Q124-b로 hci가 하위 역할로 남으므로 둘을 어떻게 할지가 새로 갈린다.

### 답이 가르는 것
hci라는 이름의 세션이 interpreter 세션으로 바뀌는 시점과, 유저 대상 몫의 지침이 어디에 사는지가 갈린다. 2단계가 끝나면 hci는 `run-interpreter.sh`로 띄우고 interpreter 지침을 읽는다.

### 선택지
- (a) **2단계를 시작한다. `hci.md`는 유저 대상 몫의 절만 남겨 `interpreter.md`가 그것을 포함하게 하고, `run-hci.sh`는 `run-interpreter.sh`를 부르는 얇은 껍데기로 둔다.** 새 파일 셋을 승인한다. 옛 이름으로 띄워도 같은 세션이 뜬다.
- (b) **2단계를 시작한다. `hci.md`와 `run-hci.sh`는 지운다.** 유저 대상 몫은 `interpreter.md`의 절이 된다. 옛 이름의 기동 경로가 없어진다.
- (c) **2단계를 뒤로 미룬다.** 구조조정 기획(Q-0060)의 답이 정해진 뒤에 다시 묻는다.

**권장:** (a). Q124-b가 hci를 하위 역할로 남겼으므로 그 지침과 기동 경로도 남기되, 원본은 interpreter 쪽 하나로 둔다. 2단계는 구조조정 기획과 겹치지 않는다.

## Q145. 동시 편집 증거로 늘어난 링크 후보 큐를 어떻게 다루는가

### 질문
반박 증거 경로(Q96-a, result 0229)를 반영하자 링크 후보가 36개에서 **323개**로 늘었다. 첫 근거가 동시 편집인 후보가 287개이고 그 가운데 `overlapsWith`(겹침)가 275개다. 사람이 판정할 큐가 그만큼 커졌으므로 어떻게 다룰지 정한다.

### 이미 정해진 것
- 새 결정 `p10-co-edit-evidence-from-small-commits`: 동시 편집 증거는 바뀐 지식 파일이 20개 이하인 커밋에서만 뽑고, 동시 편집 증거만으로는 확정하지 않는다.
- 언어모델의 셋째 자리는 판정이다(Q118-a). 판정자는 세션 둘이고 임계는 일치율이며, 판정 결과는 증거 종류 "판정"으로 적힌다.
- 후보는 확정이 아니므로 큐가 커져도 지식은 바뀌지 않는다.

### 현재 상태
관측 하나(`kb/dev/memory/obs-coedit-20261023T185726Z.md`)에 커밋 15개의 쌍 878개가 고정됐고, 링크 후보 뷰가 그것을 읽는다. 사람 정답 라벨은 10건이고 Q-0047의 20건은 답을 기다린다. 판정 증거는 아직 0건이다.

### 답이 가르는 것
큐를 사람이 직접 보는지, 판정자 세션이 먼저 걸러 일치한 것만 사람에게 올리는지, 아니면 표시만 줄이는지가 갈린다. 판정자 경로를 쓰면 판정 증거가 처음 쌓이지만 세션 비용이 든다.

### 선택지
- (a) **판정자 세션 둘이 먼저 판정하고, 일치한 후보만 사람 확인 큐에 올린다.** 판정 결과는 증거 종류 "판정"으로 쌓여 믿음 정도의 재료가 된다. 후보 287개에 세션 판정 비용이 든다.
- (b) **겹침 후보는 증거 서열과 수로 정렬해 상위 k개만 뷰에 보인다.** k는 orchestrator가 정한다. 나머지는 관측에 남아 있고 지식은 바뀌지 않는다. 판정 증거는 쌓이지 않는다.
- (c) **그대로 둔다.** 큐 323개를 사람이 본다.

**권장:** (a). 판정자 경로가 실제로 처음 쓰이는 자리이고, Q118-a와 확률적 지식 모델(지식 베이스 자체가 믿음 정도를 갖는다)의 방향에 맞는다. 비용은 유저 방침(Q-0055 추가답변)대로 이유가 되지 않는다. (b)는 표시만 줄이고 지식의 진전이 없다.

## Q146. 지운 옛 결정과의 대체 관계를 어디에 남기는가

### 질문
Q113-b로 옛 결정 트리(`chunks/decision/`)를 지웠다. 살아 있는 결정 151개가 지운 옛 결정 158개를 `supersedes`(대체)로 가리키고 있었다. 가리키는 대상이 없어진 뒤에 이 대체 관계를 어디에 남기는지 정한다.

### 이미 정해진 것
- Q113-b: 옛 결정 트리는 stable 32개를 `kb/dev/decision/`으로 옮긴 뒤 지운다(혼동을 줄이기 위해).
- 결정 `p7-decision-supersession`: 결정의 대체는 `supersedes`이고 옛 결정은 deprecated로 남는다. 결정 `p0-entity-iri-forms`: v1 잔류 항목의 IRI는 `supersedes` 대상으로만 남는다. 두 결정의 문구는 어느 답이든 트리를 지운 뒤의 상태와 맞춰 고쳐야 하고, 그 일은 0192의 결과에 들어간다.
- 새 파일은 만들기 전에 묻는다(Q66). 통일성과 건전성을 높이는 변화는 비용이 커도 진행한다(Q-0055 추가답변).

### 현재 상태
orchestrator가 이전을 마쳤다. 옛 stable 32개가 결정 기록 27개(파일 81개)가 됐고, `chunks/`는 지웠고, 시험은 123개 통과다. 시험이 124에서 123이 된 것은 옛 트리의 lint 시험 하나가 트리와 함께 없어졌기 때문이고, 검사가 약해진 것은 아니다. 지시 0192는 "supersedes를 기존 관례대로 남긴다"였다. 그러나 대상 파일이 없는 IRI를 가리키는 `supersedes`를 남기면 그래프가 그 끝점을 결정 항목으로 추론해 shape 위반 948건이 나고 게이트 시험이 실패했다. 그래서 orchestrator는 `supersedes` 175개를 결론에서 지우고, 같은 결론의 `sources`에 `git:aeb0a58:chunks/decision/<파일>` 꼴의 git 영구 링크를 더했다. hci가 세어 보니 결론 151개에 git 링크 175개가 있고 `chunks/`는 없다. 살아 있는 결정 사이의 `supersedes` 11개는 그대로다. 지금 대체 관계는 그래프에 출처(`prov:wasDerivedFrom`)로만 남는다.

### 답이 가르는 것
"이 결정이 무엇을 대체했는가"를 그래프 질의로 물을 수 있는지, 그리고 링크 끝점 규칙(한 링크 종류의 끝점은 한 종류)에 예외가 생기는지가 갈린다.

### 선택지
- (a) **지금대로 둔다.** 대체 관계는 git 영구 링크 출처로만 남는다. 새 파일도 코드 변화도 없다. 그래프 질의로는 대체 관계를 못 보고 출처 문자열을 읽어야 한다. `p0-entity-iri-forms`의 "supersedes 대상으로만 남는다" 행은 지워야 한다.
- (b) **지운 항목의 묘비(최소 노드)를 생성 그래프에 둔다.** 옛 IRI 158개를 라벨과 git 링크만 가진 `agt:retired` 노드로 생성하고, shape는 묘비를 결정 본문 검사에서 뺀다. `supersedes` 175개를 복원한다. 새 어휘 하나, 생성 파일 하나, shape 개정, 묘비 목록 파일이 든다. 새 파일은 2~3개로 예상한다(묘비 목록이 새 파일이고 정확한 수는 설계 뒤에 정해진다). 대체 관계가 다른 링크와 같은 꼴로 그래프에 남고, `p7-decision-supersession`의 "옛 결정은 deprecated로 남는다"와 가장 가깝다.
- (c) **`supersedes`의 대상에 git 링크를 허용한다.** 대상이 `git:`이면 끝점 추론을 하지 않는다. 새 파일은 없지만 한 링크 종류가 두 종류의 끝점(결정 IRI와 git 링크)을 갖게 되어 통일성이 낮아진다.

**권장:** (b). orchestrator의 권장과 같다. (a)는 정보를 출처 문자열에 숨기고 두 결정의 문구를 약하게 고치게 된다. (c)는 링크 끝점 규칙에 예외를 만든다. (b)는 비용이 들지만 유저 방침대로 통일성이 이유다. 묘비 목록을 결론의 git 링크에서 뽑을 수 있는지는 orchestrator가 설계 때 보고, 뽑을 수 있으면 새 파일은 줄어든다.

답:b

## Q147. 단일 파일 시나리오 `risk-grade-scale`을 세 항목으로 나눠 결정 본문 검사를 좁히는가

### 질문
결정 본문 shape(`decision-body-shapes`)는 지금 "역할 표지 가운데 하나 이상으로 시작한다"(`sh:or`)다. 이것을 "정확히 하나"(`sh:xone`)로 좁히면 한 파일이 두 역할을 담는 일이 검사로 막힌다. 현재 그래프에서 좁히기를 막는 파일은 `kb/vv/scenario/risk-grade-scale.md` 하나다. 이 파일을 나눠 검사를 좁히는지 정한다.

### 이미 정해진 것
- 결정 `p8-scenario-authoring`: V&V 시나리오는 세 지식 항목(`-stimulus`, `-factors`, `-excluded`)으로 나눈다. 시나리오 파일 59개 가운데 58개가 그 꼴이고 `risk-grade-scale`만 한 파일이다.
- 새 파일은 만들기 전에 묻는다(Q66). 통일성과 건전성을 높이는 변화는 비용이 커도 진행한다(Q-0055 추가답변).

### 현재 상태
결함 둘 정정(task 0234, result 0237)으로 `p8-reproducibility`의 슬롯 오검출은 없어졌고, `sh:xone`판을 현재 그래프에 대조하면 위반은 `risk-grade-scale` 1건만 남는다. 이 파일은 40줄의 stable 시나리오로, 위험 지표의 값 어휘(심각도 S0~S3, 노출 E1~E4, 탐지가능성 D1~D3)를 **결론**으로 적고 곱셈 종합 지표를 **대안**으로 기각한다. 단일 파일 결정을 다루는 코드(`weave`의 "결정 복합체 밖의 결정" 절, `DECISION_SINGLE_FILE_MARKER`)는 이 꼴 때문에 남아 있다.

### 답이 가르는 것
"한 파일 한 역할"이 검사로 강제되는지, 예외 한 파일로 남는지가 갈린다. 나누면 단일 파일 처리 코드도 소비자가 줄어 정리 대상이 된다.

### 선택지
- (a) **나눈다.** vnv가 `risk-grade-scale`을 시나리오 꼴의 세 항목으로 다시 쓴다. 새 파일은 2~3개다(원 파일이 셋 중 하나가 되면 2, 아니면 3이고 원 파일은 deprecated로 남는다). 그다음 developer가 shape를 `sh:xone`으로 좁힌다. 단일 파일 처리 코드를 지울 수 있는지는 시나리오 58건의 구조를 다시 본 뒤 정한다.
- (b) **두고 `sh:or`를 유지한다.** 비용은 없다. 한 파일이 두 역할을 담는 예외가 shape에 남고, 그 예외를 위한 코드도 남는다.

**권장:** (a). orchestrator의 권장과 같다. 남은 예외가 이 한 파일이고, 나누면 검사와 코드가 함께 단순해진다. 비용(새 파일 2~3)은 유저 방침대로 반대 이유가 되지 않는다.

## Q152. 채널 규약 검사와 메시지 이동 사이의 경쟁을 어떻게 없애는가

### 질문
`//harness:channel_lint_test`는 빌드가 분석 단계에서 채널 메시지 파일의 목록을 잡고, 실행 단계에서 그 파일들을 읽는다. 그 사이에 `mark.sh`가 메시지를 archive로 옮기면 "No such file" 오류로 빌드가 깨진다. 같은 꼴의 오류가 수신 감시의 pid 파일로 오늘 한 번 실제로 났고(07:45), pid 파일 쪽은 task 0243으로 고쳤다. 메시지 이동 쪽은 갈림길이 있어 orchestrator가 고치지 않고 물었다. 어떻게 할지 정한다.

### 이미 정해진 것
채널 메시지는 git 밖의 런타임 파일이다. 결정 `p8-verifier-env-isolation`은 검증기의 환경 격리를 요구한다.

### 현재 상태
hci와 orchestrator는 서로 언제 빌드를 돌리는지 모르고, 둘 다 수시로 `mark.sh`를 쓴다. 확률은 낮고, 깨지면 다시 돌리면 통과한다. 다만 hci가 result를 확인하는 전체 시험이 이 이유로 거짓 실패를 낼 수 있다.

### 답이 가르는 것
검사의 입력을 빌드가 추적하는지(밀폐), 검사가 실행 시점의 디렉토리를 읽는지(항상 실행)가 갈린다.

### 선택지
- (a) **channel_lint가 파일 목록 대신 채널 디렉토리를 실행 시점에 읽게 하고, 시험을 항상 다시 돌게 표시한다.** 빌드가 메시지 파일을 입력으로 잡지 않으므로 이동과 겹쳐도 깨지지 않는다. 밀폐성은 낮아지지만 대상이 git 밖 런타임 파일이라 캐시로 얻는 것이 원래 적다. 시험은 0.6초다.
- (b) **운영 규칙으로 둔다.** 빌드 중에는 `mark.sh`를 돌리지 않는다. 두 세션이 서로의 빌드를 보지 못하므로 지키기 어렵고, 드문 거짓 실패를 감수한다.

**권장:** (a). 지킬 수 없는 규칙보다 구조로 없애는 쪽이 건전하다. 새 파일은 없고 코드는 `channel_lint`와 `harness/BUILD.bazel`만 바뀐다.
