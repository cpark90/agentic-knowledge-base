# 용어·문장 3단계의 결과와 5·6단계 승인

> Q100-a는 "1~4단계를 먼저 하고, 고친 문서를 유저가 읽어 본 뒤 5·6단계를 다시 승인받는다"였다. orchestrator가 3단계(손 문서 고쳐 쓰기)를 마쳤다(result 0239). 이 질문지는 고친 문서를 읽은 뒤 답하는 것이 맞다. 4단계(경어 검사와 식별자 옆 한글 이름 검사)도 끝나(result 0246) Q100-a의 1~4단계가 모두 끝났다. orchestrator가 먼저 읽기를 권한 파일은 셋이다. `STYLEGUIDE.md`의 §0 공통(문장 규칙 아홉과 표준 용어 규칙), `docs/purpose.md`(새 규칙으로 다시 쓴 손 문서의 견본이고 궁극 목적의 정식 서술), `docs/glossary.md`(표준 용어, 옛 표기, tier)다.

## 3단계에서 된 것
- 손 문서 16개를 문장 규칙 아홉과 용어집의 표준 용어로 고쳐 썼다. 원래 22개 가운데 둘(`docs/roadmap.md`, `docs/open-questions.md`)은 검토 후속 3에서 지웠고, 설계 노트 v5는 동결(Q101-a)이고, 생성 문서 넷은 2단계에서 고쳤다.
- 읽어 볼 문서는 다음 16개다. `docs/`의 purpose, agentic-knowledge-base-structure, ontology, references, risks-and-tensions, waivers, competency-questions, tools, glossary. 뿌리의 CLAUDE.md, INTENT.md, README.md. `harness/`의 README.md, user/README.md, agents/hci.md, agents/orchestrator.md.
- 바꾼 용어는 청크 → 지식 항목, plane → 지식 종류, 스코프 → 적용 범위, 케이스 → 테스트 케이스, 판정식 → 판정 술어, 지문 → 해시값, 실측 → 측정, 재판정 → 재검증, 정의처 → 단일 정의 위치, 결정 복합체 → 결정 기록, 수준 → 정제 수준이다.
- 궁극 목적의 문장을 purpose.md, INTENT.md, README.md 세 곳에서 같은 문장으로 맞췄다. hci가 세 곳이 같은 문장임을 확인했다.
- 문장 구성의 네 수치(기호, 명사 끝, 가운뎃점 사슬, 문장 중간 괄호)가 문서마다 줄었다. 예를 들어 구조 문서는 135/67/67/100에서 1/0/1/89가 됐다. 남은 괄호는 대부분 영문 식별자를 첫 등장에 함께 적은 것이다. 토큰은 문서마다 늘었다. 정의를 먼저 쓰고 명사 나열을 문장으로 풀었기 때문이다.
- 영문 식별자, 앵커, 코드 블록, 표의 id 열은 그대로다. 바뀐 앵커 셋은 참조가 0건이다.
- 고치지 못한 옛 표기는 원본이 다른 곳에 있는 것들이다. 생성물 이름의 인용(`tools/revalidate.py`, `tools/judge.py`, `tools/metrics.py`, `tools/cq-queries/*.rq`), INTENT.md 요구 목록의 제목 넷(r-003, r-012, r-014, r-022의 `title_ko`), README와 질문지 템플릿의 코드 블록이다. 이것들은 5·6단계의 범위다.

## Q148. 고쳐 쓴 손 문서 16개를 받아들이는가 — 해석을 넣은 곳 셋

### 질문
orchestrator가 축약 메모와 은유를 완결 문장으로 풀면서 해석을 넣은 곳이 셋이다. 뜻이 맞는지 확인한다.

### 이미 정해진 것
Q104-a의 문장 규칙 아홉(정의를 먼저, 약어는 첫 등장에 풀기, 비유 금지 등)과 Q100-a의 순서다.

### 현재 상태
hci가 셋을 전후로 대조했다. 1과 3은 원문의 뜻 그대로다. 2의 첫 문장은 조금 넘친다. 채널 메시지는 git에 들어가지 않지만 `harness/channel/archive/`에 파일로는 남으므로 "기록으로 남지 않지만"보다 "git에는 남지 않지만"이 정확하다.

### 답이 가르는 것

### 선택지

- (b) **셋 모두 그대로 받아들인다.**
- (c) **일부가 틀리다.** 답에 번호와 바른 뜻을 적는다.

**권장:** (a).

## Q149. "조건 셋째 수준"의 "수준"을 어떻게 하는가

### 질문
"수준"은 Q106-a로 표준 용어 "정제 수준"으로 바꾸기로 했다. 그런데 "조건 셋째 수준"의 "수준"은 조건 분류의 깊이이고 정제 수준이 아니다. 같은 낱말이 두 뜻으로 쓰인다. 어떻게 할지 정한다.

### 이미 정해진 것
결정 `p0-one-word-one-concept`(한 낱말은 한 개념). 설계 노트 v5는 동결이라 고치지 않는다(Q101-a).

### 현재 상태
"셋째 수준"은 20곳에 있다. `docs/ontology.md` 3곳, `docs/method.md` 2곳, 동결된 노트 3곳, 결정 `p0-condition-taxonomy-extensible`의 결론과 대안(제목 포함), 그 밖의 지식 파일이다. orchestrator는 3단계에서 이것을 그대로 두고 열린 문제로 적었다.

### 답이 가르는 것
"수준"이 정제 수준 하나만 뜻하게 되는지, 두 뜻을 용어집에서 구분해 남기는지가 갈린다.

### 선택지
- (a) **조건 분류의 깊이는 다른 낱말로 바꾼다.** 예를 들어 "조건 셋째 단계"다. 낱말은 orchestrator가 표준어에서 고르고 용어집에 적는다. 결정 `p0-condition-taxonomy-extensible`의 제목과 본문이 바뀌므로 개정과 재검증이 든다. 동결된 노트의 3곳은 그대로다.
- (b) **그대로 두고 용어집에 "조건 수준(분류의 깊이)" 행을 따로 둔다.** 한 낱말 두 뜻이 용어집에 명시된 예외로 남는다.
- (c) **그대로 두고 용어집에도 적지 않는다.**

**권장:** (a). `p0-one-word-one-concept`에 맞고, 바꿀 곳이 17곳으로 많지 않다. (b)는 결정에 예외를 만든다.

## Q150. `docs/tools.md`의 긴 표 셀을 어떻게 하는가

### 질문
`docs/tools.md`의 표 셀 수십 개는 3단계에서 용어 치환까지만 했다. 셀 안의 명사 끝과 가운뎃점 나열, 화살표는 남아 있고 2천 자를 넘는 셀도 있다. 이 문서의 문장 수치가 106/28/88/302로 가장 많이 남은 이유다. 어떻게 할지 정한다.

### 이미 정해진 것
게이트 총람 표는 게이트 등록부(`defs/kb.bzl`의 GATES)의 리터럴을 손으로 옮긴 것이다. 손으로 옮긴 수치가 트리와 어긋났던 전례가 있어 README의 항목 수 여섯을 지우고 생성 뷰로 대신한 일이 있다(커밋 39c160c).

### 현재 상태
3단계는 뜻을 보존하며 셀을 다시 짜는 일을 별도 작업으로 남겼다. orchestrator는 셀을 생성물로 바꾸는 것까지 함께 검토할 수 있다고 적었다.

### 답이 가르는 것
총람 표가 손 문서로 남아 표류할 수 있는지, 등록부의 투영이 되어 표류하지 않는지가 갈린다.

### 선택지
- (a) **총람 표를 게이트 등록부에서 생성하는 투영으로 바꾸고, 손으로 쓴 셀은 없앤다.** 등록부에 없는 설명(배경, 왜 이 게이트가 있는가)은 결정의 규약 줄처럼 원본이 있는 자리로 옮긴다. 새 파일이 필요한지는 orchestrator가 설계한 뒤 알리고, 필요하면 만들기 전에 묻는다.
- (b) **손으로 다시 짠다.** 셀을 문장으로 풀되 손 문서로 남긴다. 표류 가능성은 그대로다.
- (c) **그대로 둔다.** 용어만 바뀐 상태로 남긴다.

**권장:** (a). 수치와 이름이 등록부에서 오면 표류하지 않고, 손 문서는 설명만 남아 문장 규칙을 지키기 쉬워진다. 비용은 유저 방침대로 반대 이유가 되지 않는다.

## Q151. 5·6단계(지식 파일 826개와 코드 주석)를 승인하는가

### 질문
Q100-a대로 고친 손 문서를 읽은 뒤 5단계(지식 파일 826개, 그 가운데 확정된 것 606개)와 6단계(코드 주석)를 승인하는지 정한다.

### 이미 정해진 것
- Q100-a: 1~4단계 뒤에 5·6단계를 다시 승인받는다.
- 3단계가 고치지 못한 옛 표기(요구 제목 넷, 생성물 이름, 코드 블록)는 원본이 5·6단계의 범위에 있다.
- 확정된 지식 파일을 고치면 `verified`가 풀리고 재검증이 든다. 옛 결정의 표기만 바꾸는 개정도 같다.

### 현재 상태
1~4단계가 끝났다. 5·6단계의 수량 추정(지식 파일 826개, 재검증 606개, 코드 주석의 모듈 수)은 착수 전에 orchestrator가 status로 알린다.

### 답이 가르는 것
지식 파일과 코드까지 표준 용어가 미치는지, 손 문서까지에서 멈추는지가 갈린다. 멈추면 생성 문서(AGENTS.md, STYLEGUIDE.md)의 원본인 규약 줄과 norm 절은 2단계에서 이미 고쳤으므로, 남는 옛 표기는 결정 본문과 요구 제목, 코드 주석과 생성기 문자열이다.

### 선택지
- (a) **5·6단계를 모두 승인한다.** 재검증은 표기만 바뀐 항목에 대해 orchestrator가 일괄로 한다. 단계마다 착수 전 추정치와 끝난 뒤 result가 온다.
- (b) **5단계만 승인하고 6단계는 뒤로 미룬다.** 코드 주석은 사람이 읽는 빈도가 낮다.
- (c) **둘 다 미룬다.** 손 문서를 더 읽은 뒤 다시 묻는다.

**권장:** (a). 통일성을 높이는 변화는 비용이 커도 진행한다는 방침(Q-0055 추가답변)에 맞고, 손 문서에 남은 옛 표기(요구 제목, 생성물 이름)는 5·6단계 없이는 없어지지 않는다.
