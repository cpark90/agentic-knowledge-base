# 온톨로지의 OWL 논리 검사

> **이미 정해진 것**
> - 결정 `p2-owl2-rl-profile`(추론은 OWL 2 RL로 제한한다): 추론은 OWL 2 RL 프로파일 안에서만 하고, 검사 게이트도 그 안에서 동작한다.
> - 결정 `p2-ontology-compiler-three-tiers`(온톨로지 검사기 — 온톨로지 검사 3단계): 온톨로지는 구문·스타일, 안티패턴, 논리 정합성의 세 단계를
>   통과해야 릴리스된다. 결론의 표는 앞의 두 단계에 ROBOT(`robot report`·`robot verify`)을, 셋째 단계에 OWL 추론기를 적는다.
> - 결정 `p2-ontology-module-structure`(온톨로지의 모듈 구조): 확장은 새 모듈 추가로만 하고 기존 모듈을 수정하지 않는다.
> - 결정 `p6-weakening-a-check-needs-user-approval`(검사 약화는 유저 승인 사항이다).
> - 통일성과 건전성을 높이는 변화는 비용이 커도 진행한다(Q-0055).
>
> **현재 상태** (2026-11-27, interpreter가 실측)
> - 온톨로지는 OWL로 쓰여 있다. 최상위 `kb/ontology/project-ontology.ttl`은 `owl:Ontology`이고 모듈 14개를 `owl:imports`로 가져온다.
>   모듈 파일 68개에는 OWL 클래스 76, 객체 속성 65, 값 속성 51, 개체 92, 제한 6(`owl:hasValue` 8), 서로소 공리 2, 이행·대칭·비대칭·비반사 속성
>   10이 있다. 형태 검사는 별도 SHACL 파일 29개(`kb/ontology/shapes/`)가 맡는다.
> - 게이트 `//kg:gate_test`는 OWL 추론을 돌리지 않는다. `--reason` 플래그의 기본값이 꺼짐이고(`defs/knowledge.bzl:142`) 게이트 정의
>   (`kg/BUILD.bazel:71`)가 그것을 켜지 않는다. 그래서 SHACL 앞에 RDFS 추론만 적용된다(`tools/validate.py:970`). `docs/tools.md:143`은
>   셋째 단계를 "SHACL + `--reason`(OWL-RL)"이라 적는다. 문서와 실물이 다르다.
> - 플래그를 켜도 모순은 잡히지 않는다. OWL-RL 엔진(owlrl 7.6.2)은 모순을 발견하면 그래프에 오류 노드를 더할 뿐이고(`owlrl/Closure.py:343-344`),
>   그 노드나 `owl:Nothing` 소속을 보는 shape와 질의는 저장소에 0개다. 지금 `--reason`이 하는 일은 "추론으로 늘어난 그래프에 SHACL을 다시 적용"이다.
> - 게이트를 `--test_arg=--reason`으로 한 번 돌렸다. 결과는 PASS이고 236.4초다. 끈 상태는 131.7초다. 게이트 제한은 300초(`timeout = "moderate"`)다.
>   한 번씩 잰 값이라 편차는 모른다.
> - 온톨로지 69파일과 head 그래프에 OWL-RL 추론을 따로 적용해 보았다. 트리플이 18,468에서 33,686으로 늘었고 12초 걸렸다. 오류 노드 0, `owl:Nothing`
>   소속 0이다. 지금 그래프는 OWL-RL 기준으로 모순이 없다. 스크립트는 interpreter 세션의 임시 파일이고 저장소에는 없다.
> - ROBOT은 저장소에 없다. 앞의 두 단계는 `validate.py`의 검사와 `tools/verify-queries/*.rq`가 대신한다(`docs/tools.md:141-142`).
> - 모듈 IRI는 RDF가 아니라 Bazel에 적혀 있다(`kb/ontology/BUILD.bazel`의 `kb_ontology_module(iri = …)`). 모듈 파일 어디에도 `owl:Ontology` 선언이 없다.
>   빌드는 디렉토리로 파일을 모으므로 저장소 안에서는 문제가 없다. Protégé 같은 표준 OWL 도구로 열면 import 14개를 풀지 못할 것으로 본다.
>   실제 도구로 열어 보지는 않았다.

## Q174. 셋째 단계(논리 정합성)를 실제 검사로 돌릴 것인가

### 질문
결정은 OWL 추론으로 논리 정합성을 검사한다고 적는데, 지금 게이트는 그 단계를 돌리지 않고, 플래그를 켜도 모순 자체는 판정하지 않는다.
어려운 점은 시간이다. 지금 방식대로 게이트 안에서 켜면 한 번 잰 값으로 게이트가 105초 늘어 제한 300초의 79%에 이른다.

### 답이 가르는 것
OWL 공리(서로소, `owl:hasValue` 제한, 이행 속성)가 기계 검사에 쓰이는지, 게이트 시간이 늘어나는지, 결정과 문서의 문구가 바뀌는지가 갈린다.

### 선택지
- (a) **별도 테스트 `//kg:reason_test`로 돌린다.** OWL-RL 추론을 적용한 뒤 오류 노드나 `owl:Nothing` 소속이 있으면 FAIL하고, 추론된 그래프에 SHACL을
  적용한다. `//kg:gate_test`는 지금 시간 그대로이고, `bazel test //...`에서는 두 테스트가 나란히 돈다. 비용은 테스트 하나와 판정 코드 수십 줄,
  게이트 id 하나다. 실험상 추론 자체는 12초이고, SHACL까지 합한 시간은 재 보아야 한다. 권한·방향: 바꾼다(검사 추가)
- (b) **`//kg:gate_test` 안에서 켜고 모순 판정을 더한다.** 게이트가 하나로 유지된다. 비용은 게이트가 약 236초가 되어 제한을 `long`(900초)으로
  올려야 하는 것과, 지식을 고칠 때마다 기다리는 시간이 늘어나는 것이다. 권한·방향: 바꾼다(검사 추가)
- (c) **돌리지 않고 문구를 실물에 맞춘다.** 결정 `p2-ontology-compiler-three-tiers`(온톨로지 검사기 — 온톨로지 검사 3단계)와 `docs/tools.md`에 "셋째
  단계는 아직 게이트 밖"이라고 적는다. 비용은 없고, OWL 공리는 계속 설명용으로만 남는다. 결정이 적은 검사를 실물에서 빼는 셈이므로 검사 약화로
  기록된다. 권한·방향: 그대로

**권장:** (a) — 결정이 정한 단계를 실제로 세우면서 지식을 고칠 때마다 도는 게이트의 시간은 늘리지 않는다. 지금 그래프는 모순이 없으므로 켜는 즉시
통과할 가능성이 높다.

## Q175. 결정의 ROBOT 문구를 어떻게 할 것인가

### 질문
결정 `p2-ontology-compiler-three-tiers`(온톨로지 검사기 — 온톨로지 검사 3단계)는 OBO Foundry의 ROBOT을 "그대로 쓰고 새로 만들지 않는다"고 적는다.
실제로는 ROBOT 없이 `validate.py`와 SPARQL 질의로 같은 단계를 세웠다. 어려운 점은 ROBOT이 Java 도구라 지금의 Python·Bazel 구성에 새 런타임이
들어온다는 것이다.

### 답이 가르는 것
결정 문구만 바뀌는지, 아니면 저장소에 Java 런타임과 ROBOT 의존이 들어오는지가 갈린다.

### 선택지
- (a) **문구를 실물에 맞춘다.** 결론의 도구 열을 "`validate.py` 검사와 SPARQL 질의(ROBOT의 report·verify에 해당)"로 고치고, ROBOT을 쓰지 않은
  이유를 근거에, ROBOT 도입을 대안에 기각으로 적는다. 비용은 결정 기록 하나의 개정과 재검증이다. 권한·방향: 그대로
- (b) **ROBOT을 도입한다.** Bazel에 Java 런타임과 ROBOT jar를 의존으로 더하고, `robot report`를 첫 단계로 돌린다. 비용은 새 의존과 빌드 시간,
  지금 검사와 겹치는 판정의 정리다. 권한·방향: 바꾼다(도구·의존)

**권장:** (a) — 같은 판정이 이미 게이트로 돌고 있고, 결정의 실제 요지(세 단계, 안티패턴은 SPARQL)는 지켜지고 있다.

## Q176. 표준 OWL 도구가 import를 풀 수 있게 할 것인가

### 질문
모듈 IRI가 Bazel에만 적혀 있어서, 이 저장소 밖의 OWL 도구로 온톨로지를 열면 import를 따라가지 못한다. 모듈 파일마다 `owl:Ontology` 선언을 넣는
방법은 결정 `p2-ontology-module-structure`(온톨로지의 모듈 구조)의 "기존 모듈을 수정하지 않는다"와 부딪힌다. smartbelley_vnv처럼 이 온톨로지를
코어로 쓰는 저장소가 표준 도구를 쓸 때 이 문제를 처음 만난다.

### 답이 가르는 것
온톨로지를 표준 OWL 도구로 열 수 있는지, 그리고 그것을 위해 새 생성 파일이 생기는지 기존 모듈을 고치는지가 갈린다.

### 선택지
- (a) **import 대응표를 생성한다.** Protégé와 ROBOT이 읽는 표준 형식 `catalog-v001.xml`을 `kb/ontology/BUILD.bazel`의 모듈 IRI에서 생성한다
  (`modules.bzl`처럼 생성기가 만든다). 모듈 파일은 고치지 않는다. 비용은 새 생성 파일 하나와 생성기 수정, 드리프트 검사 하나다. 권한·방향: 바꾼다(새 파일)
- (b) **모듈마다 머리 파일을 둔다.** 모듈 디렉토리 14개에 `owl:Ontology`만 선언하는 새 파일을 하나씩 더한다. 새 파일 추가이므로 모듈 구조 결정과는
  맞는다. 비용은 새 파일 14개이고, 그래도 한 모듈의 여러 파일이 그 IRI 하나로 합쳐지지 않아 도구가 다 읽지 못할 수 있다. 권한·방향: 바꾼다(새 파일)
- (c) **두고 알려진 한계로 적는다.** 결정 `p2-ontology-module-structure`(온톨로지의 모듈 구조)의 근거에 "표준 도구에서는 import가 풀리지 않는다"를
  적는다. 비용은 없다. 권한·방향: 그대로

**권장:** (a) — 모듈 파일을 건드리지 않고 표준 도구의 정해진 방식으로 푼다. 다만 표준 도구로 실제로 열어 확인하는 일을 완료조건에 넣는다.
