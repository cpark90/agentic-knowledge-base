# `usesDefinition` 의 치역을 모듈 밖으로 넓힐 것인가 (2026-10-01 중계)

원본: [`agents/orchestrator-observation-means-2026-10-01.md`](agents/orchestrator-observation-means-2026-10-01.md) ① · [`agents/orchestrator-accept-uses-definition-2026-09-30.md`](agents/orchestrator-accept-uses-definition-2026-09-30.md)

## 질문

승인(2026-09-30)대로 `usesDefinition` 을 표본에서 재고 37 파일로 넓혔다 — **476 트리플**, 게이트 56~61초(잡음대 안).
그런데 실측이 하나를 드러냈다. **모듈 안 호출은 사각지대의 63%만 덮는다.** 잎의 치역을 모듈 밖으로 넓힐 것인가.

어려운 이유는 치역 확장이 **import 해소**를 요구한다는 데 있다 — 이름이 어느 모듈의 정의인지 풀어야 하고 그 해소가 틀리면
오탐이 는다. 지금 잎은 같은 모듈의 최상위 이름만 봐서 오탐이 거의 없다.

## 이미 정해진 것

- `usesDefinition` 은 `references` 족의 잎이다. 정의역·치역 `ArtifactChunk`, 링크 키가 아니고 Bazel `deps` 가 되지 않는다.
- 표본 → 실측 → 확장의 순서(유저 승인 2026-09-30). 그 순서가 두 번(코드 추출·호출 링크) 작동했다.
- `revalidate` 의 "호출부" 수치는 **같은 모듈 안의 상한**이라고 문서에 경계를 적었다.

## 현재 상태 (실측 2026-09-30)

- `tools/` 최상위 호출 간선 **739** 중 모듈 안 **465** · 모듈 간 **274**(37%).
- 채널이 근거로 든 사례 — `pct` 개명 → 호출부 36 파손 — 는 **전부 모듈 간**이라 지금 잎으로는 **0** 이 나온다. 가장 아팠던 사례를 지금 잎이 못 본다.
- 모듈 간 교차 트리플 0. 방출 경계의 정의처는 `defs/kb.bzl` 의 `EXTRACTED_SOURCES` 하나다.

## 답이 가르는 것

- **넓히면** 274 간선이 링크가 되고 `pct` 사례가 잡힌다. 대신 import 해소기가 필요하고 오탐이 생기며 링크 1,279 → 1,550 안팎, 게이트 시간이 는다(지금 여유 약 60초).
- **두면** `revalidate` 의 호출부 수치는 모듈 안 상한으로 남고 모듈 간 파손은 타입 체커·테스트가 잡는다. 경계는 이미 문서에 있다.
- **표본으로 먼저 재면** 가장 많이 호출되는 모듈 쌍 하나(`kb_lib` ← 나머지)에서 해소 정확도와 오탐률을 보고 넓힐지 정한다.

## 선택지

1. **표본 쌍 하나로 먼저 잰다** (권고). `kb_lib` 을 치역으로 두는 모듈 간 호출만 먼저 낸다 — 274 중 대부분이 그쪽이다. 해소 정확도·오탐·게이트 시간을 관측하고 넓힌다. 비용: 추출기 한 절 + 관측 하나.
2. **치역을 전부 넓힌다.** 비용: import 해소기 + 274 트리플 + 오탐 관리.
3. **두고 경계만 유지한다.** 비용 없음. `pct` 류 파손은 그래프 밖(타입 체커·테스트)에 둔다.
