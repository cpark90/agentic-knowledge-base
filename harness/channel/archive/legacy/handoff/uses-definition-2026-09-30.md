# 코드의 호출 관계를 링크로 — 표본 먼저 (2026-09-30 승인, 사후 기록)

유저 답: *"1."* — **표본 하나에서 모듈 안 호출만 먼저 내고 링크 밀도·게이트 시간을 잰 뒤 넓힌다.**

**이 항목은 사후 기록이다.** 승인 태깅 직후 담당 역할이 반영을 시작해 hci 의 인수인계보다 앞섰다. 반영을 허가하는 신호는
승인 태깅이므로 규약 위반이 아니다 — 다만 파급효과·계획을 미리 적지 못했으므로 여기에는 **확인한 결과**를 남긴다.

## 파급효과 (반영 뒤 확인)

- 어휘 잎 `usesDefinition` 은 `references` 족이라 **링크 키가 아니고 Bazel `deps` 가 되지 않는다.** TIM 밖이다. 함수 churn 이 빌드 그래프를 건드리지 않는다는 성질이 유지된다.
- 개명의 사각지대가 좁혀진다 — 그래프 재판정 9 대 코드 파손 36 이던 차이를 `revalidate` 가 링크로 덮는다.
- 게이트 시간의 여유가 변수다. 확장 뒤 `//kg:gate_test` 가 55초였고 상한이 120초다.

## 반영 계획 (승인 시점의 것)

1. developer — 어휘 잎 하나(`references` 족 아래)와 추출기의 한 절(AST 의 최상위 이름 참조, 같은 모듈 한정).
2. developer — `revalidate` 가 "본문이 바뀐 청크를 가리키는 `usesDefinition` 의 출발점"을 재판정 대상으로 낸다.
3. vnv — 표본의 링크 수·게이트 시간을 관측으로 남긴다. **그 수치가 37 파일 확장의 근거다.**
4. orchestrator — `docs/rules.md` 의 링크 족 표와 `revalidate` 수치의 뜻(지식 churn + 코드 파손 상한).

## 확인 못 한 것

- 표본에서 생길 링크 수를 hci 가 세지 못했다(측정 중 다른 지시를 받았다). vnv 의 관측이 그 수를 낸다.
- 모듈 간 호출은 이 범위 밖이다 — 같은 모듈 한정이라 모듈을 가로지르는 호출은 링크로 남지 않는다.

## 판정

`apply` 다. 표본 → 실측 → 확장의 순서가 코드 추출에서 한 번 작동했고 같은 순서다.
