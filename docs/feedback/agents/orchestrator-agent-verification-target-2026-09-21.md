# 에이전트 검증의 `verifies` 도착점 — 결정과 규칙이 어긋난다 (2026-09-21)

## 질문

에이전트 검증의 `verifies` 는 무엇을 가리키는가. 결정은 하네스·스코프 개체라 하고, 규칙은 개발 KB 청크만 허용한다. 둘 중 하나를 고쳐야 요구 `r-025` 가 성립할 수 있다. 어려운 이유는 둘 다 stable 이고 한쪽은 유저 승인을 거친 게이트라는 것이다 — 규칙을 넓히면 검사 약화(유저 승인 사항)이고, 결정을 좁히면 검증 대상 둘이라는 설계가 바뀐다.

## 이미 정해진 것

- `p8-two-verification-targets/conclusion.md` — "제품 검증은 `decision`·`contract` 의 logical 기준을, 에이전트 검증은 **하네스·스코프 개체**를 검증한다." `verifies` 의 도착점이 다르다고 명시한다.
- `defs/kb.bzl:73-79` — `verifies` 의 주어는 V&V KB 청크뿐, **대상은 개발 KB 청크**, 같은 수준끼리. 하네스·스코프 개체(`kg/catalog-kg.ttl` 의 `id:h-akb`·`id:scope-*`)는 청크가 아니라 A-Box 개체라 `ChunkInfo` 가 없고 이 규칙의 대상이 될 수 없다.
- `r-025-verify-product-and-agent` — "제품과 에이전트 둘 다 검증한다."

## 현재 상태 (실측 2026-09-21)

- vnv 가 요구 17건의 사슬을 만들며 `r-025` 는 **사람 확인**으로 분류했다(`kb/vv/goal/agent-and-product-verified.md` + 기준, 케이스 없음). 에이전트 쪽 사슬은 0 이다. `audit` 검증 현황: 목표 33 · 케이스까지 이어진 목표 28 — 차이 5 중 하나가 이것이다.
- 에이전트 검증의 자극은 "작업 집합과 유저 피드백", 판정은 "산출물 품질과 인지능력(11.3절)" 이다. 산출물 품질은 이미 게이트(`writer`·`endorse`·`gendoc`)가 잰다. 인지능력의 판정 수단은 저장소에 없다.

## 답이 가르는 것

- **규칙을 넓히면** `verifies` 의 대상에 카탈로그 개체가 들어온다. `defs/kb.bzl` 의 분석 시점 검사가 A-Box 개체를 알아야 하고(지금은 청크 타깃만 안다), 수준 일치 검사는 개체에 수준이 없어 적용할 수 없다. TIM 의 `verifies` 칸이 하나 늘어난다.
- **결정을 좁히면** 에이전트 검증도 개발 KB 청크를 도착점으로 한다 — 예를 들어 역할·스코프를 정한 결정(`pe-*`·`p11-*`)이나 요구 `r-019`(읽기·쓰기 집합 기록)를 검증한다. `p8-two-verification-targets` 의 결론 셋째 줄을 고치고 `supersedes` 로 잇는다. 검증 대상 둘이라는 구분은 남되 도착점 종류는 하나가 된다.
- **둘 다 두면** `r-025` 는 영구히 사람 확인이고 케이스까지 이어진 목표 비율의 상한이 100% 아래에 고정된다.

## 선택지

1. **결정을 좁힌다** — 에이전트 검증의 도착점도 개발 KB 청크(역할·스코프·작업 집합을 정한 결정과 요구)로 한다. 규칙은 그대로다. 비용: 결정 하나 개정(orchestrator), 에이전트 쪽 사슬 저작(vnv). 산출물 품질 게이트가 이미 그 자리를 잰다는 실측이 근거다.
2. **규칙을 넓힌다** — `verifies` 대상에 카탈로그 개체를 허용한다. 비용: `defs/kb.bzl` 개정과 검사 약화 승인(유저), 개체 참조 방식 설계(청크 타깃이 아닌 IRI), 수준 검사의 예외. 인지능력 판정 수단이 생길 때 필요한 형태다.
3. **지금은 둔다** — `r-025` 를 사람 확인으로 유지하고 인지능력 판정 수단이 생길 때 다시 본다. 비용: 케이스 이어진 비율의 상한이 고정된다.

orchestrator 권장은 1 이다.
