# `usesDefinition` 치역 — 표본 쌍 하나로 먼저 (2026-10-01 승인)

유저 답: *"1."* — **`kb_lib` 을 치역으로 두는 모듈 간 호출만 먼저 낸다.** 해소 정확도·오탐·게이트 시간을 관측하고 넓힌다.
표본 → 실측 → 확장의 순서가 세 번째 적용된다.

## 파급효과

- 모듈 간 호출 간선 **274** 가운데 `kb_lib` 을 향하는 것이 대부분이다(단일 정의처 규칙의 결과). 표본 하나로 사각지대의 큰 몫이 덮인다.
- `pct` 개명 → 36 파손 사례가 **처음으로 잡힌다** — 그 호출부가 전부 `kb_lib` 쪽이다. 승인 당시의 근거 사례가 표본에서 검증된다.
- import 해소기가 처음 들어온다. 같은 모듈 한정이던 추출기가 `from tools import kb_lib`·`kb_lib.x` 형태를 풀어야 한다. 해소 실패는 링크를 내지 않고 **관측에 센다**(오탐보다 누락이 낫다).
- 링크 개체 1,279 → 약 1,500, `//kg:gate_test` 시간이 는다. 여유 약 60초가 분모다.
- 닿지 않는 것: 링크 키·TIM·`deps`. `references` 족이라 빌드 그래프에 들지 않는다.

## 반영 계획

1. **developer — 추출기.** 치역을 `kb_lib` 한 모듈로 넓히는 갈래를 더한다. 해소는 **최상위 import 와 `모듈.이름` 꼴**만 — 동적 접근·별칭 재지정은 해소하지 않고 누락 수로 센다. 방출 경계는 `defs/kb.bzl` 의 `EXTRACTED_SOURCES` 옆에 치역 선언 하나로 둔다.
2. **vnv — 관측.** 생성된 모듈 간 링크 수 · 해소 실패 수 · 오탐 표본 검사(무작위 20건 손 확인) · `//kg:gate_test` 시간. `pct` 사례가 `revalidate` 에서 36 안팎으로 나오는지가 **성공 조건**이다.
3. **orchestrator — 경계 문서.** `revalidate` 의 "호출부" 뜻을 "같은 모듈 + `kb_lib` 치역"으로 고친다. 넓힐지의 판단은 2번의 수치를 받아 항목으로 다시 올린다.

**검색 키워드**: `usesDefinition` · `EXTRACTED_SOURCES` · `치역` · `모듈 간` · `import` · `호출부` · `revalidate`.

## 확인 못 한 것

- 274 중 `kb_lib` 향이 정확히 몇인지. "대부분"은 단일 정의처 규칙에서 추정했고 추출기가 센다.
- 별칭(`import kb_lib as k`)·재수출의 빈도. 적을 것이나 세지 않았다.

## 판정

`apply` 다. 세 번째 표본 순서이고 성공 조건(`pct` 사례의 포착)이 수치로 정해져 있다.
