# 청크의 단위를 토큰으로 — 숫자는 42의 배수, 토크나이저는 고정 (2026-10-01 승인)

유저 답: *"1. 42의 배수로 — P.S. 공개 토크나이저 하나를 의존성으로 고정"*. 곧 **단위는 토큰이고, 상한은 실측으로 정하되
42의 배수**이며, 계수기는 **공개 토크나이저 하나를 의존성으로 고정**한다.

## 파급효과

- **규칙의 자리 전부가 바뀐다.** 노트 938·949행(기획 원본), 황금률 4(`AGENTS.md`), STYLEGUIDE §0·§4, shape `agt:lineCount`, `chunk_lint`, `kb_lib` 상수, 결정 `p1-context-budget-breakdown`(예산 200줄도 토큰으로 환산한다), `artifact` 의 별도 상한 200줄.
- **토크나이저가 의존성이다.** 게이트가 재현되려면 어휘 파일을 저장소에 고정하고 네트워크 없이 로드해야 한다. ODD 에 선례가 있다 — 학습 모델 임베딩을 "모델·버전 고정이 조건에 없다"는 이유로 명시 제외했다. 토크나이저는 그 반대 경로로 **조건을 먼저 추가**한다(`id:cond-dependency-lock` 확장 또는 조건 신설).
- **숫자에 따라 분할 수가 갈린다.** 근사 계수(한글 3자/토큰)로 42의 배수마다 초과 수를 냈다. 실 토크나이저로 다시 재야 한다.

| 상한 | 초과 청크(근사) | 비율 |
|---|---|---|
| 42×6 = 252 | 413 | 25% |
| 42×7 = 294 | 318 | 19% |
| 42×8 = 336 | 256 | 15% |
| 42×10 = 420 | 189 | 11% |
| 42×15 = 630 | 111 | 6% |

- 조망 근거(한 번에 4~5개)로 역산하면 **예산 ÷ 5**가 상한이다. 예산 200줄 ≈ 3,200토큰이면 630 근처(42×15), 참조 저장소의 재결정 260 은 42×6 근처다. **둘 중 어느 근거를 쓰는가가 orchestrator 의 결정**이다.
- 분할된 청크는 `p10-split-keeps-work-identity` 규율을 따른다 — 조각 하나가 uuid 를 승계하고 나머지는 `specializationOf`. 도장이 있는 청크를 쪼개면 재판정이 따른다.
- 닿지 않는 것: 링크 종류·plane·level·역할. 단위 변경은 **크기 규칙** 하나의 교체다.

## 반영 계획

1. **developer — 토크나이저 고정.** 공개 BPE 어휘 파일 하나를 저장소(또는 Bazel 외부 저장소의 고정 해시)에 두고 오프라인 로드한다. 후보는 공개 어휘 파일을 배포하는 계수기 가운데 **한글 토큰 효율이 알려진 것**이다. 선택 근거를 결정 본문에 적는다. `requirements`·`MODULE.bazel` 고정과 ODD 조건 추가가 같은 커밋이다.
2. **vnv — 실측.** 고정된 계수기로 청크 1,628 의 본문 토큰 분포를 내고 42의 배수마다 초과 수를 관측으로 남긴다. 예산 200줄의 토큰 환산도 같은 계수기로 잰다.
3. **orchestrator — 숫자 결정.** 조망 단위(예산 ÷ 5)와 참조 저장소의 재결정(260) 가운데 근거를 고르고 42의 배수로 확정한다. `p1-context-budget-breakdown` 을 `supersedes` 로 개정하고, **노트 938·949·641행을 유저 의도대로 정정**한다(기획 원본의 오기록을 바로잡는 것이므로 동결 전에 한다). 황금률 4·STYLEGUIDE §0·§4 가 따른다.
4. **developer — 게이트 교체.** `agt:lineCount` → 토큰 수 속성, shape·`chunk_lint`·`kb_lib` 상수·`metrics` 의 크기 분포(41~42줄 근접 비율 → 토큰 근접 비율). `artifact` 의 별도 상한도 같은 배수 체계로.
5. **역할별 분할.** 초과 청크를 plane 의 write 권한대로 쪼갠다 — 결정은 orchestrator, V&V 는 vnv, `artifact` 는 추출기가 다시 낸다. 도장 있는 청크는 `endorse` 재판정.
6. **vnv — 음성 시험.** 상한 +1 토큰 청크가 FAIL 인지, 토크나이저 어휘 파일이 바뀌면 지문이 바뀌어 게이트가 잡는지.

**검색 키워드**: `42줄` · `42 lines` · `lineCount` · `줄 예산` · `200줄` · `토큰` · `tokenizer` · `조망` · `4~5개` · `p1-context-budget`.

## 확인 못 한 것

- **실제 토크나이저 수치.** 위 표는 근사(한글 3자/토큰)다. 계수기에 따라 20~40% 다를 수 있다 — 2번이 낸다.
- **토크나이저 선택.** hci 는 "공개 어휘 파일 + 오프라인 로드"라는 조건만 적었다. 어느 것인지는 developer 가 한글 효율·라이선스·어휘 파일 크기로 정한다.
- 예산 200줄의 토큰 환산값. 조망 근거의 분모가 그것이다.
- 분할의 규모. 숫자가 252 면 400여 건, 630 이면 100여 건이다 — 3번의 결정이 5번의 비용을 정한다.

## 판정

숫자 없이 분할을 시작하지 않는다. 기획 원본(노트)의 정정이 들어 있다는 점이 통일 기획 1-②(유저 의도 대 노트) 의 첫 실행이다.
