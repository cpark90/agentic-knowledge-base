# 하나의 서비스로 — 통일과 최적화 기획 (2026-10-01)

원문: [`inquiries/unification-request-2026-10-01.md`](inquiries/unification-request-2026-10-01.md)

## 질문

유저 지적 — 상위 기획은 맞는데 **세부가 기획과 다르고**, 전체가 **하나의 서비스로 통일되지 않고 산발적**이다.
무엇을 기준으로 다듬고 무엇부터 할 것인가.

어려운 이유는 둘이다. 첫째, **"하나의 서비스"의 정의가 저장소에 없다.** 산출물이 셋(온톨로지·방법·도구)이라는 결정은
있으나 셋이 어떤 한 흐름을 이루는지는 문장으로 고정돼 있지 않다. 정의 없이는 통일의 기준이 없다. 둘째, **기획과
구현의 어긋남을 재는 수단이 없다.** 지금 지표는 "노트의 절을 인용했는가"(156/157)를 재지 "인용한 대로 만들었는가"를
재지 않는다.

## 이미 정해진 것

- 산출물은 셋뿐이다 — 온톨로지·방법·도구. 결정은 참조로 동결한다(2026-09-02 재정렬, 자기목적화 리스크의 대응).
- 문서는 생성물이다(`p12-documents-are-generated`). 수치를 손으로 적지 않는다.
- 규약 상수의 단일 정의처는 `kb_lib` 하나다(STYLEGUIDE §7). 값 어휘·허용표는 `defs/kb.bzl` 로 통일했다(2026-09-27).
- 게이트는 강화만 한다. 약화는 유저 승인 사항이다.
- 기획의 원본은 노트 v5(`docs/agent-knowledge-system-notes.md`, 3,475줄, `[확정]` 394문장)다.
- 하네스는 저장소의 지식 진전을 반영해 스스로 개선해야 한다(유저 지시 2026-09-23 — 요구로 세우기로 했으나 아직 없다).
- 참조 저장소에 **intent-fidelity 감사**의 선례가 있다 — 의도를 요소로 원자화하고 요소마다 일치·부분·대체·미표현 넷으로 판정한다.

## 답이 가르는 것

- **서비스를 먼저 정의하면** 통일의 기준이 생긴다. hci 의 읽기는 한 순환이다 — **지식 파일 → 게이트 → 뷰·활용 → 관측 → 되먹임**. 도구 37은 그 순환의 동사들이고, 문서 15는 그 순환의 투영이다. 정의가 다르면(예: 에이전트 하네스 제품, 또는 지식 베이스 자체) 통일 축이 바뀐다.
- **충실도 감사를 먼저 하면** "기획과 다른 세부"가 목록이 된다. 그 목록의 항목마다 기획을 따를지 구현을 따를지 결정이 하나씩 생긴다. 감사 없이 도구만 통합하면 산발은 줄되 어긋남은 남는다.
- **도구·문서 통합만 하면** 눈에 보이는 산발이 줄고 로더 11 → 1, 진입점 37 → 1 이 된다. 기획 어긋남은 그대로다.
- **첫 형태 완결을 먼저 하면** 로드맵이 전진하되 산발이 늘 수 있다 — 지금까지 첫 형태가 쌓인 방식이 그것이다.

## 기획안 — 단계 여섯

| 단계 | 무엇 | 산출 | 담당 |
|---|---|---|---|
| **0. 서비스 정의** | "하나의 서비스"를 결정 하나로 못박는다 — 순환 다섯 마디, 진입점 하나, 데이터 모델 하나(union + `kb_lib`), 출력 규약 하나(gendoc), 문서 체계 하나(생성 뷰 + 규범 문서 넷) | 결정 1 + 요구 1(하네스 자기개선) | orchestrator |
| **1. 충실도 감사** | 노트 `[확정]` 394문장을 요소로 원자화하고 요소마다 **일치 / 부분 / 대체 / 미표현**을 판정한다. 수치의 계보(기획값 → 결정값 → 구현값)와 용어의 지시 대상 표를 함께 낸다 | 어긋남 목록(관측) + 항목마다 "기획 따름/구현 따름" 결정 | vnv 판정 · orchestrator 결정 |
| **2. 도구 통합** | 로더 11 → `kb_lib` 하나 · 진입점 37 → 통합 CLI 하나(`bazel run //tools:akb -- <동사>`) · FAIL id 카탈로그(44 → 등록·중복 제거) · skill = 도구 1:1(17 생성) · 뷰 매크로 하나 | 도구 재배선, 생성 BUILD | developer |
| **3. 문서 통합** | 생성 가능한 손 문서를 뷰로(`tools.md` 총람·`roadmap.md` 상태·`competency-questions.md` 상태) · 규범 문서는 넷(AGENTS·STYLEGUIDE·rules·method)으로 고정 · 노트는 **기획 원본으로 동결**하고 결정이 대체한 절은 표시 | 손 문서 15 → 규범 4 + 생성 뷰 | orchestrator·developer |
| **4. 첫 형태 완결** | 단계 5(abstract·logical 결정 — 건너뜀 432 → 0)·7(변이 검출·수기 케이스 0)·8(거짓 빈 칸)을 통과 조건까지. 6단계 착수 | 로드맵 통과 표시 | 역할 셋 |
| **5. 되먹임 고정** | 하네스 자기개선 요구를 stable 로 올리고 "지식이 늘면 규칙·도구가 따라온다"의 경로(일반화 → 승격 → 게이트)를 검증 사슬로 묶는다 | 요구 + V&V 사슬 | orchestrator·vnv |

**순서의 근거.** 0 이 없으면 2·3 의 통일 기준이 없다. 1 이 없으면 "기획과 다른 세부"가 목록이 되지 않는다. 2·3 은
1 의 결과를 받아 함께 돌고, 4·5 는 그 뒤다. 0 과 1 은 결정·판정이라 코드 변경이 없고, 2 부터 코드가 바뀐다.

## 선택지

1. **0 → 1 → 2·3 → 4 → 5 전부** (권고). 정의와 감사가 앞서고 통합이 그 결과를 받는다. 비용: 0 은 결정 하나, 1 은 394문장의 판정(판정자 둘 + 미끼 — 세션 판정자 규약대로), 2·3 은 도구·문서 재배선, 4·5 는 로드맵 그 자체.
2. **2·3 만 — 도구·문서 통합.** 눈에 보이는 산발을 먼저 없앤다. 비용: 작다. 기획 어긋남은 미해결로 남고 통일 기준 없이 통합하므로 두 번 손댈 수 있다.
3. **0 → 1 만 먼저.** 서비스 정의와 충실도 감사 결과를 본 뒤 2~5 를 다시 기획한다. 비용: 결정 하나 + 감사 하나. 가장 신중하고 가장 느리다.

## 함께 답할 것

**"하나의 서비스"가 무엇인가.** hci 는 **지식 파일 → 게이트 → 뷰·활용 → 관측 → 되먹임**의 한 순환으로 읽었다. 유저가
생각하는 서비스가 그것과 다르면(에이전트 하네스를 제품으로 보는지, 지식 베이스 자체를 보는지) 0 단계의 결정이 달라지고
통일의 축이 바뀐다. 한 문장이면 된다.

## 정의에 따른 재조정 (hci, 2026-10-01, 2차 — 유저 정정 반영)

유저 정정(2026-10-01): *"진입점에서 언급한 skill 집합이 서비스의 API라는 점은 기획과 다름. 에이전트가 작업을 수행할 때 context에
포함되는 구조화된 지식 자체와 지식과 작업을 연결하는 방법론, 작업을 수행하는 프로세스를 제공하는 것이 지식 베이스의 역할임.
일종의 에이전트의 지식 자체와 지식사용에 관한 매우 정돈되고 기능화된 위키임. 한편, 서비스에서 벗어나는 부분들을 제거하는
대응이 아닌 산발적인 부분들을 포함될 수 있게 수정하여 통일성있게 다듬는 것이 필요함."*

hci 의 1차 재조정 둘을 철회한다. **skill 은 API 가 아니고**, **서비스 밖을 빼는 것이 아니라 안으로 들인다.**

### 서비스 — 세 층의 위키

| 층 | 무엇 | 에이전트에게 어떻게 닿는가 | 지금 저장소의 실물 |
|---|---|---|---|
| **지식** | 작업 중 컨텍스트에 들어가는 구조화된 지식 자체 | 작업 집합(`workset`)으로 컨텍스트에 실린다 | 청크 1,478 · 온톨로지 · ODD · 그래프 |
| **방법론** | 지식과 작업을 잇는 방법 — 어떤 작업에 어떤 지식을, 어떤 규칙으로 | 작업 집합의 조립 규칙과 그 안의 규칙 청크 | `docs/method.md`·`rules.md`·STYLEGUIDE(손 문서) · 결정 661 |
| **프로세스** | 작업을 수행하는 절차 — 저작·판정·검증·반영의 순서 | 절차 청크와 그것을 실행하는 도구·skill | 도구 37(이제 청크 630) · 게이트 71 · skill 20 · 채널 규약 |

**서비스의 접점은 컨텍스트 하나다.** 에이전트가 받는 것은 skill 이나 CLI 가 아니라 **작업 집합에 실린 세 층의 지식**이다.
skill·도구·게이트는 프로세스 층의 **실행 표면**이지 서비스의 입구가 아니다. 1차 재조정의 "접점 셋(읽기·쓰기·믿기)" 분류는
접근 방식의 구분이지 서비스 정의가 아니므로 버린다.

### 산발의 뜻이 달라진다

산발은 "서비스 밖의 것이 많다"가 아니라 **세 층 어디에도 자리를 받지 못한 것이 있다**는 뜻이다. 처리는 제거가 아니라
**편입**이다 — 산발적인 각 조각이 세 층 가운데 어느 층의 어떤 항목인지 정하고, 그 층의 형식으로 **다시 쓴다**.

| 산발의 실물 | 어느 층으로 편입하는가 | 어떻게 |
|---|---|---|
| 도구 37, 각자 그래프를 여는 로더 11 | **프로세스** | 도구 = 절차 청크 + 구현 청크(이미 추출됨). 로더는 한 절차로 통일하고 그 절차도 청크다 |
| 게이트 71, FAIL id 44 | **방법론**(규칙) + **프로세스**(판정 절차) | 규칙마다 방법론 청크 하나, 판정 절차는 프로세스 청크. id 카탈로그는 생성 뷰 |
| 손 문서 15 | **방법론** | 규범 문서 넷(AGENTS·STYLEGUIDE·rules·method)은 방법론 층의 **투영(생성 뷰)**이 되고 원본은 청크다. 노트는 기획 원본으로 밖에 둔다 |
| skill 20 대 도구 37 | **프로세스**의 실행 표면 | skill 은 프로세스 청크에서 생성한다(`gen_skills` 가 이미 그 형태). 공백 17은 "프로세스 청크가 없는 도구"이고 청크를 쓴다 |
| 뷰 11, 매크로 각자 | **지식**의 투영 | 뷰 = 지식 층의 질의. 매크로 하나로 통일하되 뷰마다 질의 청크가 원본 |
| 채널(`docs/feedback/`) | **프로세스**(유저 소통 절차) | 규약은 프로세스 청크, 항목은 운영 기록으로 그래프 밖 유지 |
| 로드맵의 "첫 형태" 19 | 세 층 어디든 | 첫 형태마다 어느 층의 어떤 항목인지 적고 완결 조건을 그 층의 형식으로 |

### 단계의 수정 (2차)

- **0. 서비스 정의** — 결정 문장: **"지식 베이스는 에이전트의 컨텍스트에 실리는 세 층 — 지식·방법론·프로세스 — 의 정돈된 위키다. 저장소의 모든 것은 세 층 중 하나의 항목이거나 그 항목의 투영이다."** 세 층을 어휘로 올리고(기존 plane 과의 관계를 정한다 — plane 은 지식의 종류, 층은 지식의 **역할**), 항목마다 층을 표시한다.
- **1. 감사** — ① 노트 `[확정]` 394문장의 충실도(기획 vs 구현) ② **층 배정 감사** — 도구·게이트·뷰·skill·문서·규약 전부에 층을 배정한다. 배정되지 않는 것이 산발의 목록이고, 그것은 빼지 않고 **다시 쓴다**.
- **2. 편입** — ②의 목록을 층의 형식으로 다시 쓴다. 도구 → 절차 청크, 게이트 → 규칙 청크 + 판정 절차, 손 문서 → 청크 + 생성 뷰. 로더·매크로 통일은 그 과정의 부산물이다.
- **3. 투영** — 규범 문서 넷을 생성 뷰로 바꾸고 노트를 기획 원본으로 동결한다.
- **4·5** — 그대로.

### 주의 하나 — 지식 층의 내용

지식 베이스의 내용(결정 661·요구 76)이 전부 **이 체계 자신의 설계**라는 실측은 그대로다. 위키 정의로 보면 그것은 "소프트웨어
개발"이라는 첫 분야의 지식이고 **자기 자신이 첫 사례**다. 편입 작업은 그 사실을 바꾸지 않는다. 두 번째 분야(프로파일)가
들어올 때 세 층이 분야를 넘어 재사용되는지가 위키 정의의 첫 시험이다.
