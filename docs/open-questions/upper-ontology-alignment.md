# 상위 온톨로지의 continuant / occurrent 구분을 어떻게 적용하는가

## 질문
표준 상위 온톨로지(BFO)는 세계를 continuant(시간을 관통해 존재하는 것 — 물체·정보 내용·
역할)와 occurrent(시간 안에서 일어나는 것 — 과정·사건)로 가른다. 이 체계의 개체들(청크·
구성체·결정·링크·가정·scene·실행 기록·역할)이 각각 어느 쪽인지, 그 구분이 어휘·shape·
질의에 무엇을 요구하는지가 정해지지 않았다. 어려운 이유는 **분류가 틀리면 나중에 전부
다시 봐야 하기 때문**이다 — `part-of`가 continuant용과 occurrent용으로 갈리므로 링크
타입의 정의역·치역 공리가 그 위에 얹힌다.

## 이미 정해진 것
- 맨바닥에서 짓지 않고 표준 상위 온톨로지 위에 구축한다 (d-0047).
- 개체는 여러 scene을 관통하는 endurant이고 정체성은 IRI, 상태 변화는 `prov:wasRevisionOf`
  (d-0051).
- 온톨로지는 사다리 전체가 쓰는 어휘다 (d-0046) — 상위 온톨로지 선택이 모든 plane에 걸린다.

## 현재 상태
`upper` 모듈이 없다. `agt:KnowledgeItem` 정의문이 "상위 온톨로지 도입 시
`iao:InformationContentEntity` 아래로 정렬한다"고 예고만 하고, `agt:hasDirectPart`도 "표준
part-of의 하위 속성으로 정렬 예정"이다. `tools/kb_lib.py`에 obo 접두어만 등록되어 있다.
occurrent 쪽 개체(실행 기록·scene·시나리오)는 아직 하나도 없다.

## 답이 가르는 것
링크 타입(traceability)의 공리가 이 분류 위에 놓인다. **연결 단계 전에 정하면 한 번,
후에 정하면 링크 전체를 재검토**한다.

## 선택지
- **A. BFO+IAO 도입, 있는 것만 정렬** — 청크·구성체·결정·가정·링크 = 정보 내용 개체,
  역할 = `bfo:role`. occurrent 쪽은 실행 기록이 생길 때. BFO 준수 검사를 위생 항목에 예약.
- **B. 자체 최소 구분** — `agt:Continuant`/`agt:Occurrent` 두 클래스만. 표준어 우선 원칙과
  충돌한다.
- **C. 보류** — 실행 기록이 생길 때까지. 링크 공리를 나중에 재검토하는 비용을 감수한다.
