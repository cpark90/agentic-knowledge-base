# `contract`·`artifact`의 logical 내용이 무엇인가

## 질문
계층는 모든 plane이 다섯 level을 갖는다고 한다. 그러나 시그니처(`contract`)와 구현
(`artifact`)은 현재 관행에서 후보 공간을 남기지 않고 곧바로 확정된다. 이 두 plane의
**logical 칸**(선택지 공간: 도메인 + 제약)에 실제로 무엇이 들어가는가 — `decision`의
logical을 다른 각도에서 본 것에 불과한가, 아니면 "시그니처 후보 집합"·"알고리즘 후보
집합" 같은 독립적 내용이 있는가?

## 이미 정해진 것
- 이 칸이 격자의 시험대다 — 채울 수 있는지가 "계층는 일반 메커니즘"이라는 주장의 검증
  (d-0084, 대안절에 이 질문이 미확정으로 적혀 있다).
- logical은 근거의 보존소다 — 선택되지 않은 대안과 배제 이유가 여기 남는다 (d-0005).
- logical의 파일 형식은 `-space`(변수·후보·제약) (d-0100).
- 뷰은 저장하지 않고 질의로 조립한다 (d-0075) — "뷰에 불과"하다면 파일을 만들면 안 된다.
- **인터페이스가 추적성의 기준축이다**(유저 Q3 2026-09-03). 이는 `contract`가 매트릭스의
  행 키가 된다는 뜻이므로 독립 내용 쪽에 무게를 싣는다.

## 현재 상태
`contract`·`artifact` 항목이 0이고 `space/`가 비어 있어 실물로 검증할 수 없다.

## 답이 가르는 것
`-space` 파일을 plane마다 두는가, `decision`에만 두는가. 그리고 [설계 논증의
형식화](design-argument-formalization.md)의 답과 맞물린다 — 그쪽이 부정이면 `decision`의
logical이 얇아지므로 이 질문이 자동으로 "독립 내용" 쪽으로 기운다.

## 선택지
- **A. 뷰이다** — 격자 표에서 이 칸을 "(뷰)"으로 표기하고 파일을 만들지 않는다.
- **B. 독립 내용이다** — 시그니처 후보·구현 후보를 각 plane의 `-space`로 두고 `decision`의
  후보와 `refines`로 잇는다.
- **C. 실험 후 결정** — 실제 함수 하나의 시그니처 후보 공간(예외 / 결과 객체 / 목록 반환)을
  두 방식으로 다 써 보고 정한다.
