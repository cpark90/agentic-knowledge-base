# 리팩터링 시 개체가 새로 생기는 것을 어떻게 막는가

## 질문
항목을 분할·병합·이동·개명하면 "같은 것"인가 "새 것"인가? 정체성이 끊기면 그 IRI를 끝으로
하는 링크와 가정이 전부 고아가 된다. 설계는 "IRI가 지속하고 변화는 `wasRevisionOf`"라고
하지만, **언제 IRI를 유지하고 언제 새 IRI를 만들지의 판정 기준**과 그것을 강제할 장치가 없다.

## 이미 정해진 것
- 개체는 endurant, 정체성 = IRI, 변화 = `prov:wasRevisionOf` 연쇄 (d-0051).
- 지속 IRI(불투명) + 버전 IRI(내용 해시). 본문이 같으면 해시가 같다 (d-0032).
- 분할·병합은 **새 IRI**를 만들고 옛 IRI를 `prov:wasDerivedFrom`으로 잇는다 (d-0002 · d-0077).
- 삭제하지 않고 폐기한다 — `owl:deprecated` + 대체 지정 (d-0035).

## 현재 상태
IRI는 순번(`chunk-d0001`)이라 불투명하지만 uuid는 아니다. 파일명(라벨 슬러그)과 IRI가
분리되어 있어 개명은 IRI를 깨지 않는다. **버전 IRI·내용 해시가 없고** `prov:wasRevisionOf`
사용은 0이다. 분해 과정에서 이미 분할·병합 사례가 생겼으나 상호 `wasDerivedFrom` 없이
출처 문서 하나만 가리킨다.

## 답이 가르는 것
두 가지 위험이 갈린다 — (i) 본문만 고쳤는데 새 항목으로 취급되는 **과잉 신생**은 해시 버전
IRI가 막고, (ii) 실제로는 같은 지식인데 새 파일을 만들어 버리는 **중복 신생**은 검색 우선
규약과 라벨 중복 검사가 막는다. 어느 쪽이 더 큰 위험인지 실측이 없다.

## 선택지
- **A. 편집 프로토콜을 게이트로** — 새 파일은 `derived_from` 필수, 라벨 유사도가 높은 기존
  항목이 있으면 경고. 본문 변경은 같은 IRI + 해시 버전.
- **B. 해시 유사도 임계** — 유사도가 임계 이상이면 같은 개체로 자동 판정. 산문에는 부정확하다.
- **C. 리뷰 규약만** — 연결 단계 전까지 `STYLEGUIDE.md`의 `[지킴]`으로.
