# 미해결 질문

두 종류를 구분한다. **체계의 미해결**은 설계가 아직 답하지 못한 것이고,
**구현의 미해결**은 답은 정해졌으나 이 저장소가 아직 하지 않은 것이다. 섞으면
"설계가 덜 됐다"와 "아직 안 만들었다"가 뒤엉킨다.

원래 노트 Part XV였다. 노트는 *"미해결 항목이 23개 남아 있는 동안 이 문서는
설계 노트다"* 라고 스스로를 규정했다 — 그 판정 기준을 여기가 이어받는다.

## 1. 체계의 미해결 — 26건

### 1순위 — 골격을 정하는 문제

| # | 질문 | 관련 |
|---|---|---|
| 1 | 상위 온톨로지의 continuant / occurrent 구분을 어떻게 적용하는가 | 온톨로지 기반 |
| 2 | `contract`·`artifact`의 **logical 내용**이 무엇인가 — `decision`의 투영에 불과한가, 독립적 내용을 갖는가 | plane × level 격자의 시험대 |
| 3 | **설계 논증을 형식화할 수 있는가** — `decision`의 functional → abstract 전이가 성립하는가 | 사다리의 성립 조건 |
| 4 | 구성체 수준 가정이 따로 필요한가, 부분 청크 가정의 합집합으로 충분한가 | 가정 입도 |
| 5 | 리팩터링 시 시간 정체성 — 개체가 새로 생기는 것을 어떻게 막는가 | 정체성 단절 리스크 |

2번과 3번이 서로 맞물린다. 3번이 부정이면 `decision`은 abstract 이하만 갖고,
그러면 2번의 "투영에 불과한가"가 다른 문제가 된다.

### 2순위

|---|---|
| 6 | 상승의 트리거 — 언제 관측을 명세로 올리는가 |
| 7 | `annotation`의 plane 순서 — `artifact`보다 상위인가 하위인가 |
| 8 | 링크 판정 근거 — 후보를 확정으로 올리는 판단을 무엇으로 하는가 |
| 9 | plane 수의 상한 (현재 6, 후보 `requirement`·`ui`) |
| 10 | 커버리지 계산 방법 |

### 3순위

| # | 질문 |
|---|---|
| 11 | 기존에 없는 모듈화를 어떻게 구현하는가 |
| 12 | 영구 보관 정보와 실시간 수정 정보의 구분 (다수 인원 작업 시) |
| 13 | 평가 metric 선택 |
| 14 | 미명명·미검출 오류 — 알려지지 않은 **요인**과 알려지지 않은 **조합** 중 어느 쪽이 다수인가 |
| 15 | ODD의 적정 크기 |

| 22 | 시뮬레이션 프로젝트의 최소 구성 — 실제 서비스의 어느 서브셋이면 에이전트 검증에 충분한가 |
| 23 | 6단계 관측을 커버리지에서 배제하는 것이 과도한가 |

### 분해가 드러낸 것

Part XV의 23건은 노트가 스스로 모아 둔 목록이었다. 분해하면서 **본문 절에는
있으나 그 목록에 오르지 못한** 질문이 셋 나왔다:

| # | 질문 | 출처 |
|---|---|---|
| 24 | 프로파일 간에 공유해야 할 것이 도메인 중립 골격 외에 더 있는가 (예: "리뷰 코멘트"처럼 여러 프로파일에 공통으로 나타나는 개념) | 노트 2.11절 |
| 25 | 42줄 강제가 시스템 묘사를 손상시키는 plane이 있는가 | 노트 11.2절 |
| 26 | 두 원인(어휘 문제 / 커버리지 문제) 중 어느 쪽이 실제 실패의 다수인가 — 실행 기록이 쌓여야 안다 | 노트 10.1절 |

목록과 본문이 어긋나 있었다는 뜻이며, 흩어진 `[?]`를 한곳에 모으는 것이 이
문서의 존재 이유다. 25번은 16번(42줄의 plane별 적정성)과, 26번은 14번(미명명·
미검출 오류)과 이웃한 질문이지만 같지 않다 — 16번은 상한값을, 25번은 강제
자체의 부작용을 묻는다.

### 균형점이 미정인 설계 긴장

[`risks-and-tensions.md`](risks-and-tensions.md)의 **역할 세분화 vs 오염 전파** —
나눌수록 완성도가 오르지만 채널이 늘수록 오염 경로가 늘어난다. 균형점은 실측 후.

## 2. 구현의 미해결 — 이 저장소가 아직 안 한 것

답은 정해져 있고 만들기만 하면 되는 것들이다. 체계의 미해결과 달리 **막혀
있지 않다.**

| 항목 | 무엇이 없나 | 원본 |
|---|---|---|
| 9.6절 입력 검증 게이트 | 카탈로그 정합성(역할별 read plane 최소 1, 설계/구현/운영의 write plane 비공유, `maxConcurrent` 합) 이 규약으로만 지켜진다 | [`gate-design.md`](gate-design.md) |
| 고아 검사 | 청크가 어느 구성체의 부분인지 기계가 보지 않는다 | [`gate-design.md`](gate-design.md) |
| 결정 청크 역할 태그 검사 | 결론·근거·대안 존재 여부를 검사하지 않는다 | [`gate-design.md`](gate-design.md) |
| 정규화 게이트 | `canonicalize.py --check`가 있으나 테스트 타깃이 아니다 | [`gate-design.md`](gate-design.md) |
| 이름 붙은 그래프 | 네 그래프가 논리적 구분일 뿐 — Turtle이라 물리적으로 하나 | [`storage-design.md`](storage-design.md) |
| 내용 해시 IRI | 버전 IRI가 없어 해시 변경으로 재판정을 촉발할 수 없다 | [`storage-design.md`](storage-design.md) |
| `artifact` plane 등록 | 도구 코드를 청크로 등록할지 미결 | [`artifact-placement.md`](artifact-placement.md) §3.1 |
| 지표 자동 측정 | 청크 수·고아율을 손으로 센다 | [`roadmap.md`](roadmap.md) |
| 읽기·쓰기 집합 기록 | 하네스가 기록하지 않아 3단계 링크 구축의 입력이 없다 | [`roadmap.md`](roadmap.md) |

## 3. 이 목록을 쓰는 법

- **새 질문이 생기면 여기 추가한다.** 청크로 만들지 않는다 — 결론이 없는 것은
  결정 청크가 될 수 없다.
- **질문이 풀리면 여기서 지우고 결정 청크를 만든다.** 그 청크가 답이고, 여기
  남기면 이중 관리가 된다.
- 1절의 26건이 0이 되면 이 체계는 더 이상 초안이 아니다. 노트는 23건을 세었고,
  분해가 3건을 더 찾았다 — 세는 일 자체가 감사였다.
