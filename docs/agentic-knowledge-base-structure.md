# Agentic Knowledge Base — 구조도

> 설계 노트 `agent-knowledge-system-notes.md`의 운용 지도다. 괄호 안의 번호는 노트의 절 번호다.

**이 문서는 설계 지도다.** 이 문서는 실제 저장소가 아니라 노트가 설계한 체계를 그린다. 그래서 여기 적힌
도구와 모듈 가운데 일부는 저장소에 없고, 없는 것에는 "(미구현)"을 붙인다(2026-10-24 확인). 무엇이
구현되었는가의 원본은 생성 뷰와 `defs/kb.bzl`이다. 도구 목록은 `tools/BUILD.bazel`이, 게이트 목록은
`bazel query 'tests(//...)'`가, 현재 상태는 `bazel build //kg:metrics`가 낸다.

이 문서는 다음 용어를 쓴다. 단위 지식(식별자 `chunk`)은 한 파일에 담긴 한 주제의 지식이다. 지식
종류(식별자 `plane`)는 단위 지식을 검증 방법에 따라 나눈 갈래다. 정제 수준(식별자 `level`, 줄여서
"수준")은 같은 지식을 얼마나 구체적으로 적었는가의 단계다. 표준 용어의 원본은 [`glossary.md`](glossary.md)다.

## 궁극 목적

- 궁극 목적의 원본은 `INTENT.md`다. 확률적 지식 모델은 링크와 결정 후보가 증거에서 계산한 믿음 정도를 갖는 지식 베이스 자체다(Q-0063 Q153).
- **축적의 단위** (12.7)
    - 프로젝트를 넘어 쌓이는 것은 온톨로지 어휘와 일반화로 올라간 제약(공리), ODD 코어, 결함 어휘, 교훈이다.
    - **지식은 프로젝트를 넘지 않는다.** 지식은 그 프로젝트의 ODD 안에서만 유효하다.
- **검증 대상은 둘이다** (8.8). 하나는 만들어지는 제품이고, 다른 하나는 그것을 만드는 에이전트다.
- **지식 베이스는 둘이다** (8.1). 개발 KB와 V&V KB를 나누는 이유는 독립성이고, 둘을 연동하는 이유는 정제를 끝까지 잇기 위해서다.
- 대상 지식
    - **시스템을 만들기 위한 지식은 개발 KB에 둔다.** 이 지식은 정제 계층을 따라 정제한 산출이고, 상세는 아래 development KB 블록에 있다.
        - 요구는 `requirement` 지식 종류이고 **functional 수준에만 둔다.** 요구는 자연어로 쓰되 EARS를 권장하고, 이해관계자와 관심사를 밝힌다. 요구의 판정은 합의로 한다 (5.1, 6.1).
        - 의도의 틀은 ODD다. ODD는 모든 요구가 성립하는 조건의 전체 집합이다. ODD는 온톨로지의 프로젝트 뷰이고, 선별과 값 할당, 폐쇄로 만든다 (3.1).
        - 후보는 `-space` 설계 공간에 둔다. 설계 공간은 변수와 후보 링크, 양립 제약을 담고 logical 수준에 있다 (9.4).
        - 결정은 `decision` 지식 종류이고 결론과 근거, 대안의 복합체다. **결정은 어느 요구의 어느 관심사에 기여하는지 밝힌다** (6.8).
        - 계약은 `contract` 지식 종류이고 인터페이스를 정의한다.
        - 스키마는 `schema` 지식 종류다.
        - 가정은 모든 지식이 기대는 전제이고, ODD 조건 위의 명제다 (6.5).
        - 합격 기준은 V&V KB로 옮겼다. 아래 V&V KB 항목을 본다.
        - 역량 질문은 온톨로지가 답해야 하는 질문의 목록이고, 요구이자 완료 판정 기준이다. 노트의 목록은 CQ1부터 CQ20까지다 (2.7).
            - CQ19는 "executable까지 닿지 않은 요구는 무엇인가"이고, CQ20은 "요구로 거슬러 오르지 못하는 산출물은 무엇인가"이다.
        - 구현은 `artifact` 지식 종류이고 **executable 수준에만 둔다** (6.1).
    - **검증과 확인을 위한 지식은 V&V KB에 둔다** (8.2). V&V KB는 코어의 두 번째 인스턴스이고, 지식 종류마다 담는 실체만 다르다. 상세는 아래 V&V KB 블록에 있다.
        - 검증 목표는 `requirement`에 두고, 요구에서 `derives-from`으로 파생한다.
        - **시나리오**는 `decision`에 둔다. 시나리오는 자극(결론 자리)과 요인(근거 자리), 배제 자극(대안 자리)으로 이루어지고, 변수는 ODD 속성이다.
        - 합격 기준은 `contract`에 두고, **logical 수준의 판정 술어다.** 합격 기준은 검증기와 검증 대상 사이의 계약이고, 기준 없는 `verifies`는 거부한다.
        - 테스트 케이스 형식은 `schema`에 둔다.
        - 검증기는 `artifact`의 executable 수준에 둔다. **`verifies`의 주어는 V&V KB의 지식뿐이다.**
        - 판정 주석은 `annotation`에 두고 결함을 분류한다.
    - **시스템에 대한 지식**은 정제 계층을 따른 일반화의 입력이다.
        - 관측은 실행 기록 `agt:Run`이고 V&V KB의 `memory`에 둔다. 관측은 concrete 수준에만 두고, 추가만 하며 고치지 않는다(append-only). **시간 정보는 관측과 `prov:wasRevisionOf`만 담는다** (0.5).
        - 주석은 `annotation` 지식 종류이고 판정과 리뷰, 설명을 담는다. 주석의 수준은 대상의 수준을 물려받는다 (6.4).
        - 기억은 `memory` 지식 종류다. 기억은 단기 기억이고, 첫 실행 때 한 번에 읽는다 (11.4).
        - 결함은 관측에서 추론한 실패다. 결함은 세 갈래와 ODC 유형, 한정자, 트리거의 조합으로 분류한다 (11.1).
        - 교훈은 기억이나 관측에서 승격한 지식이다. 교훈은 개발 KB에서 **요구와 결정, 규칙**이 되고, V&V KB에서 **시나리오와 기준**이 된다 (6.3).
    - **순환**은 만들기 위한 지식에서 시스템, 시스템에 대한 지식, 교훈을 거쳐 다시 만들기 위한 지식으로 돌아온다.
        - 정제는 `refines`를 남기고 일반화는 `prov:wasDerivedFrom`을 남기므로, 순환 자체를 추적할 수 있다.
        - 일반화는 지식에서 그치지 않고 온톨로지까지 닿아야 한다.

## Agentic Knowledge Base

### methodology — 지식을 축적·운용하는 전체 순서와 그 이유

방법론은 다음 순서로 돈다. 정제와 V&V 파생은 서로 오가며 진행하고, 마지막 일반화에서 얻은 교훈은 다시
프로파일과 ODD, 요구, 시나리오, 결정으로 돌아간다.

1. 프로파일 구축
1. 프로젝트 ODD 작성
1. 정제(저작)와 **V&V 파생**
1. 조회
1. 연결
1. 갱신
1. 뷰
1. 일반화

| 단계 | 전제 | 완료 판정 |
|---|---|---|
| 프로파일 구축 | 코어 온톨로지 | 품질 검사를 통과하고 코어를 수정하지 않는다 (2.11) |
| ODD 작성 | 프로파일의 조건 어휘 | 5단계 절차를 통과한다 (3.8) |
| 정제(저작) | ODD. ODD가 없으면 적용 범위와 가정을 만들 수 없다 | 게이트 4종을 통과하고 `refines` 연쇄가 functional까지 닿는다 (6.8) |
| 조회 | ODD와 에이전트 카탈로그의 조합인 적용 범위 | 작업 집합이 컨텍스트 예산 안에 든다 (1.4) |
| 연결 | 하네스의 읽기와 쓰기 기록 | 링크 밀도가 하한 이상이고 구축 비율을 측정한다 (10.14) |
| 갱신 | A~B등급의 가정 판정 술어 | 전수 조사 없이 무효 범위를 계산한다 (6.10) |
| 뷰 | 링크와 복합체 | 뷰는 질의로만 생성하고 사본을 두지 않는다 (4.6) |
| V&V 파생 | 개발 KB의 요구와 범위, 구현 | 각 수준에 검증 대응물(목표, 기준, 검증기)이 있다 (8.3) |
| 일반화 | 쌓인 실행 기록 | 온톨로지 확장이 한 건 이상이고, 사후 분석마다 산출이 있다 (12.12) |

- 방법론과 도입 순서는 다르다. 방법론은 운용의 순환이고, 도입 순서는 체계를 세우는 8단계다(Part XIV, 단계별 작업과 통과 조건은 14.1). 1~6단계는 개발 KB, 7단계는 V&V KB, 8단계는 복원과 감사를 세운다. 도입은 사례 프로젝트 하나에서 끝까지 진행하고(부록 B), 도입 1단계만으로 이득이 없으면 중단한다.

### input — 체계가 소모하는 파라미터 (Part XI)

- 입력은 도메인 프로파일과 에이전트 카탈로그, 실행 모드, 메모리 승격 규칙, 재검증 시점, 태그 어휘, 판정 도구 바인딩, 앵커 해석기, 단위 지식 상한, 일반화 임계값, 커버리지 임계, 후보 상한이다.
- 입력은 전부 온톨로지 어휘로 적고 버전을 관리한다. 입력 사이에는 의존 순서가 있다 (11.7).

### result

결과물은 코어(공통)와 그 위의 두 지식 베이스로 이루어진다. 그래서 ontology와 tools, rules, method를 각각
**코어, development, V&V**의 셋으로 나눠 적는다.

#### 두 지식 베이스의 정의

| | development KB (Part VII) | V&V KB (Part VIII) |
|---|---|---|
| 목적 | 요구사항 명세에서 실제 산출물을 만들기 위한 지식 | 요구와 산출물의 전 과정에 연동해 시나리오 기반 검증과 확인을 수행하기 위한 지식 |
| 정제 계층 | 요구, 형식화, 범위와 제약, 값, 구현의 차례 | 검증 목표, 시나리오 형식화, 논리 시나리오와 기준, 테스트 케이스, 검증기의 차례 |
| 완료 판정 | 정제 완주와 후방 추적 귀속 100%, 계약 선행, 대안 기록, 가정 유효, **V&V `verifies` 유효**를 모두 만족한다 (7.9) | 목표 파생과 기준 바인딩, V&V 완주가 100%이고, 변이를 검출하며, 독립성 위반이 0건이다 (8.26) |
| 편집 주체 | design, developer, orchestrator | V&V engineer, 검증기 저자, executor, judge |
| 상대 KB 접근 | V&V KB를 **읽기만** 한다 | 개발 KB를 읽고 `verifies`로 참조한다 |
| 지표 | 전방 추적 커버리지, 후방 추적 커버리지, 결정 완결률, `-space` 체류, 계약 선행률, 대안 기록률 (7.8) | 목표 파생률, 기준 바인딩률, V&V 완주율, 실행 통과율, 변이 검출률, 재현 실패율, 검증 대응물 지연 (8.26) |

- **ontology** — 지식의 코어와 뼈대
    - 코어 (공통)
        - 코어는 분야와 무관하다. 코어는 지식 종류와 수준, 조건, 가정, 역할, 그리고 단위 지식과 복합체, 링크 타입을 정의한다.
        - 코어는 상위 온톨로지(BFO/IAO) 위에 세우고, 최상위 분류를 지어내지 않는다 (2.2).
        - 모듈은 `entity/`와 `related/`, `vv/`(미구현), `profile/`, `defect`, `defect-rules`다 (2.3). `entity/`는 지식 종류별 모듈이다. `related/`는 조건과 적용 범위, 가정, workset, revision, trace, 하네스를 가로지르는 모듈이고, workset과 revision의 어휘는 `related/state/`에 있다.
        - 어휘와 형식화를 나눈다. `defect`는 분류만 담고, `defect-rules`는 추론 규칙을 담는다.
        - **온톨로지 검사 3단계** (2.5)는 report(구문과 스타일), verify(SPARQL 안티패턴, 게이트 대부분이 여기 있다), reason(불만족과 의도하지 않은 동치)이다. 빌드 시스템이 이 검사를 컴파일 단계처럼 돌린다.
        - 용어 제안 워크플로 (2.5)는 에이전트가 template 행을 내면 온톨로지 검사 3단계를 거쳐 유저가 승인하고 확장 모듈에 넣는 순서다. 이 워크플로는 에이전트를 신뢰할 수 없는 센서로 다룬다.
        - 사례에서 얻은 교훈 (2.12)은 다섯이다. 코어는 수십 클래스로 충분하다. 게이트는 질의로 만든다. `sources`가 빈 단위 지식은 실패다. 신뢰 등급은 전파한다. 판정 이력은 head에 둔다.
        - 관계는 RO의 하위 속성으로 정의하고 (2.8), 추론은 OWL 2 RL 안에서 한다 (2.9). 시간에 따른 정체성은 IRI를 유지하고 `prov:wasRevisionOf`로 잇는다 (2.6).
        - 분야 프로파일은 코어를 **확장만** 하는 모듈 `profile/<분야>`다 (2.11, 부록 D).
    - development
        - `entity/`는 `norm`을 뺀 지식 종류마다 개발 실체를 정의한다 (7.2). `RequirementChunk`는 EARS 패턴과 이해관계자, 관심사 필드를 갖는다. `DecisionChunk`는 결론과 근거, 대안의 역할 태그와 `serves`를 갖는다. `ContractChunk`는 시그니처와 사전조건, 사후조건을 갖는다. `SchemaChunk`는 호환 관계를 갖는다. `ArtifactChunk`는 구현과 앵커를 갖는다. 나머지는 `AnnotationChunk`와 `MemoryChunk`다.
        - 개발 어휘는 EARS 다섯 패턴과 관심사 분류, 계약 호환성(하위 호환과 비호환), 표본 추출 근거 유형이다.
        - 개발 KB가 맡는 역량 질문은 CQ1 충족, CQ3 배제 대안, CQ4 무효 범위, CQ7 고아, CQ16 할당, **CQ19 정제 완주**, **CQ20 후방 추적 귀속**이다 (2.7).
    - V&V
        - `vv/` 모듈(미구현)은 `norm`을 뺀 지식 종류마다 V&V 실체를 정의한다 (8.2). 그 실체는 검증 목표와 **시나리오**(자극, 요인, 배제 자극), 합격 기준(판정 술어), 테스트 케이스 형식, 검증기, 판정 주석, 실행 기록이다.
        - 위험 분석 (8.21)은 다섯을 낸다. 현상(ODD 조건과 `defect` 요인), 인과(`defect-rules`), 지표, **시나리오 부류의 abstract 라이브러리**(프로젝트를 넘어 재사용한다), 목표 거동(Runbook)이다.
        - 시나리오 도메인 모델은 actor(에이전트, 유저, 서비스)와 action으로 이루어지고, OpenSCENARIO DSL의 구조에 이 체계의 도메인을 얹는다 (부록 E).
        - 결함 어휘는 세 갈래와 ODC 유형, 한정자, 트리거, 발견 단계로 이루어진다 (8.16~8.18).
        - V&V KB가 맡는 역량 질문은 CQ5 작업 집합, CQ6 ODD 안팎, CQ10 결함 요인, **CQ11 무엇을 검증하는가**, CQ17 양립 후보다.
- **tools** — ontology와 method, rules를 수행하고 관리하는 도구

- **rules** — 지식을 모델링하기 위한 규칙
    - 코어 (공통)
        - 단위 지식의 규칙 (4.1~4.11)
            - 본문은 토큰 상한(`p1-chunk-unit-is-tokens`) 이하다.
            - 한 단위 지식은 지식 종류 하나와 수준 하나, 주제 하나, 파일 하나를 갖는다.
            - 단위 지식은 네 갈래의 이름 그래프를 갖고, IRI는 uuid와 해시로 만든다.
            - 라벨이 단위 지식의 인터페이스다. 단위 지식은 상태 기계를 따르고, 분할과 병합의 규칙이 있다.
        - 복합체의 규칙 (4.5)
            - 복합체는 `part-of`로 부분을 묶고, 부분은 같은 지식 종류와 같은 수준이어야 한다.
            - 부분의 수는 7±2이고, 순서는 `co:List`로 적는다. 부분은 참조로 재사용하고, 상태는 부분에서 집계한다.
        - 지식 종류는 판정 방식으로 정의한다. 목록은 `defs/kb.bzl`의 `PLANES`와 결정 `p5-plane-by-verification`이 정한다. 지식 종류 사이의 영향은 단방향 규칙을 따르고, 새 지식 종류를 더하는 기준이 있다 (5.1~5.5).
        - 정제 수준은 요구에서 산출물로 내려가는 단계다. 다섯 수준마다 허용되는 지식 종류가 있고, 허용 밖에 둔 단위 지식은 shape 위반이다 (6.1, 6.4).
        - 추적성의 규칙 (10.1~10.12)
            - 추적성은 TIM을 따르고, 링크 타입은 12종이다. 지식 종류를 가로지르는 링크는 `assumes`뿐이다.
            - 링크는 구축으로 얻는 것을 우선하고, 후보를 거쳐 확정한다. 링크는 본문 밖(frontmatter)에 두고, 상태를 갖고, 매트릭스로 본다.
        - **후보의 구조** (9.10, 9.11)
            - 확정의 판정은 가능과 불가능 두 값의 가능 집합이고, 제약 검사로 결정론적으로 정한다(`p9-feasible-set-for-settlement`).
            - 증거 기록에서 계산한 믿음 정도는 후보와 링크 곁에 병기한다. 믿음 정도는 부분순서의 동률만 깨고, 상태와 가능 집합은 바꾸지 않는다(`p9-evidence-ledger-with-belief`, `p9-preference-partial-order`, Q90-a와 Q109-b).
            - 모든 링크는 `when` 조건(ODD와 가정 위의 CEL)을 갖는다. `when`은 `assumes`와 적용 범위 conditional의 일반형이고, 링크의 상태는 조건을 평가한 결과다.
            - 후보에는 **증거 기록**이 붙는다. 증거 종류의 목록과 서열, 지지와 반박의 극성은 `p9-evidence-ledger-with-belief`가 정한다.
            - 상태 전이는 증거 기록 규칙을 따른다. 구축이나 실행의 지지가 없으면 확정하지 않는다. 실행의 반박이 있으면 즉시 기각한다. 지지와 반박이 함께 있으면 유저 확인 대기열로 보낸다. 유저 결정은 서열 밖에 있는 확정 권한이다(Q111-a).
            - 언어모델은 후보와 선호를 제안하고, 믿음 정도는 증거 기록에서 계산한다. 반면 확정은 증거 기록 규칙과 게이트가 한다.
        - 지식 그래프의 규칙 (Part III, 0.5)
            - ODD는 뷰이고, 모든 조건의 전체 집합이다. ODD 조건에는 판정 방법이 반드시 있고, 시간 제약 어휘를 쓰며, ODD 이탈은 신호로 다룬다.
            - 그래프는 리비전과 작업 집합을 갖되, 시간열 개체는 두지 않는다. 가정은 ODD 위에 서고, 통제 어휘와 태그를 쓴다.
    - development (7.2~7.7)
        - `requirement`는 functional 수준에만 두고, EARS 패턴과 이해관계자, 관심사가 필수다.
        - 결정은 항상 결론과 근거, 대안의 세 단위 지식으로 이루어진 복합체다. **대안이 없는 결정은 shape 위반이다.** 대안이 없었다는 사실도 대안에 기록한다.
        - 결정은 수준마다 별개의 단위 지식으로 두고 `refines`로 잇는다. 결정은 concrete 단위 지식이 생겨야 확정된다.
        - **계약이 우선한다.** `contract`의 abstract 단위 지식이 구현보다 먼저 있어야 한다. 계약 없는 구현은 정제가 끊긴 것이다.
        - 스키마는 `decision`에서 `derives-from`으로 파생하고 `contract`를 `constrains`한다. 비호환 변경은 새 IRI와 `supersedes`로 한다.
        - `artifact`는 구현만 담고, 검증기는 V&V KB에 둔다.
        - developer는 concrete 결정과 확정된 스키마가 없으면 구현하지 못한다(적용 범위 conditional). developer의 작업 집합에는 `-space`가 없다.
        - 결정의 대체는 `supersedes`로 한다. 대체된 옛 결정은 deprecated가 되고, 그 결정의 `satisfies`는 모두 suspect가 된다.
        - 완료는 V&V KB의 `verifies`가 유효한지 읽은 뒤에만 선언할 수 있다.
    - V&V (8.2~8.5, 8.11~8.15)
        - **독립성**: 개발 역할은 V&V KB에 쓰지 못하고, 기준은 요구를 고쳐서만 바꾼다. 두 KB는 저장을 분리하고, 의존은 V&V에서 개발로 향하는 한 방향뿐이다.
        - **검증 대응물이 필수다.** functional에서 abstract로의 정제에는 검증 목표가, logical에서 concrete로의 정제에는 합격 기준이, concrete에서 executable로의 정제에는 검증기가 있어야 한다. 없으면 개발 게이트가 실패한다.
        - KB를 가로지르는 링크는 `verifies`뿐이다. `verifies`는 V&V에서 개발로 향하고, 같은 수준끼리만 잇는다.
        - 시나리오는 V&V KB의 `decision` 복합체이고, 자극과 요인, 배제 자극으로 이루어진다. 변수는 ODD 속성만 쓴다. ODD 밖의 자극은 `odd:outside`로 표시하고 커버리지에서 뺀다.
        - **기준과 자극은 다르다.** 기준은 V&V KB의 `contract`에 별개의 단위 지식으로 두고, `verifies` 속성으로 바인딩한다. 판정 술어가 없는 기준은 abstract 수준으로 내린다.
        - concrete 테스트 케이스는 사람이 쓰지 않고 `keep`과 `cover`에서 생성한다. 표본 근거가 없는 테스트 케이스는 거부한다.
        - 검증기의 저자는 V&V engineer와 다른 사람(또는 다른 세션)이어야 한다.
        - 재현할 수 없는 결과는 검증 환경 5~6단계로 내린다. 6단계의 관측은 커버리지에 넣지 않는다.
        - 학습된 판정자는 선택과 판별, 캘리브레이션의 3지표를 통과하고 사람의 승인을 받아야 한다. 판정 결과는 head의 `verified` 목록에 쌓는다.
        - 시뮬레이션 신뢰도는 요인별로 본다. 상관을 검증하지 않은 요인이 3단계에서 통과한 결과는 커버리지에 넣지 않는다.
        - 확인 결과는 `requirement`로 간다. 이것이 요구가 바뀌는 유일한 정규 경로다.
        - **불일치의 귀속은 결정이다** (8.4). 귀속처는 산출물, 지식(요구 과도, 제약 부족, 가정 누락), 또는 둘 다다. 귀속은 V&V `decision`의 **지침**(귀속, 조치, 배제된 전략)에 적고, 진단은 기호 도구를 먼저 쓴다.
        - 검증기의 결과는 개발 KB `satisfies` 후보의 증거 기록에 지지(+)나 반박(−)으로 들어간다. 결과는 링크가 아니라 증거 기록 항목이므로 방향 규칙이 유지된다 (9.11).
- **method** — 지식을 모델링하기 위한 구체적인 방법
    - 코어 (공통)
        - 저작 쪽 절차는 프로파일 구축 (2.11)과 ODD 작성 5단계 (3.8), 적용 범위 파생 (3.4), 단위 지식 저작 (4.10), 후보 관리 (9.4)다.
        - 연결은 세 컨텍스트 사이의 인수인계로 하고, 복원은 k≤7로 한다 (10.3, 10.4).
        - 갱신은 판정과 8단계 전파, 재검증의 차례로 한다 (6.10, 10.11, 9.8).
        - 그 밖의 절차는 조회 (5.6)와 뷰 (4.6), 영향 분석 (12.6), 안전 정지 (3.10), 온보딩 (12.8)이다.
        - 일반화는 관측에서 도메인, 변수, 개념의 차례로 올라가고, 목적지는 요구와 기준, 결정, 규칙이다 (6.3, 6.11).
    - development (7.3~7.9)
        - **저작 흐름 8단계**는 요구 작성, 형식화(`serves`), 계약 선언, 전개(`-space`와 사후조건, 필드 범위), 확정(체크박스 되먹임), 스키마 확정, 구현, 리뷰의 차례다. 2~6단계는 design이, 7단계는 developer가 맡는다.
        - 정제 전이 게이트 4종 (6.8)은 functional에서 abstract로의 기여 명시, abstract에서 logical로의 판정 술어, logical에서 concrete로의 표본 근거, concrete에서 executable로의 기준 바인딩이다.
        - 결정의 확정은 `-space`에서 유저 체크박스를 거쳐 후보 하나를 고르고, concrete 결론과 대안으로 승격하는 차례다.
        - 계약 선언에서 구현으로 갈 때는 시그니처를 먼저 쓰고, 사후조건은 V&V 기준의 재료가 된다.
        - 스키마 확정은 호환성을 판정한 뒤 `wasRevisionOf`나 새 IRI로 한다.
        - 요구 사이의 순서는 `depends-on`과 시간 제약 어휘로 적고, 요구마다 따로 정제한다.
        - 완료 판정 5조건은 연쇄 완주와 계약 선행, 대안 존재, 가정 유효, V&V 유효다.
    - V&V (8.19~8.25)
        - **위험 분석 G1~G6** (8.21)은 현상 추출, 인과 모델, 데이터 검토, 지표, 시나리오 부류, 목표 거동의 차례다. 규칙성 가정을 먼저 세운다. 처음에는 전문가가 하고, 이후 관측으로 보정한다. 위험 분석은 도메인마다 한 번 한다.
        - **워크플로 10단계** (8.19)는 목표 파생, 시나리오 형식화, 논리 시나리오와 기준, 테스트 케이스 생성, 검증기, 환경 할당, 실행, 판정, 보고, 되먹임의 차례다. 1~3단계는 개발이 확정되기 전에 시작한다.
        - V&V 파생 (8.3)은 다섯 대응으로 한다. 요구에서 목표를, abstract 결정에서 abstract 시나리오를, 계약 사후조건에서 기준을, 확정 값에서 테스트 케이스를, 구현에서 검증기를 파생한다.
        - 시나리오 저작 (8.22)은 부류에서 시작해 ODD 속성으로 변수를 잡고, 계약 사후조건으로 기준을 세우고, 배제 자극을 기록하는 차례다.
        - 테스트 케이스 생성 5규칙 (8.23)은 등가 분할과 경계값(따로 센다), t-wise, 요인 주입, 관측 재현이다.
        - 환경 할당 (8.10)은 판정이 가능한 가장 낮은 단계를 고른다. 요인마다 단계를 정하고, 재현성 조건을 적는다.
        - 검증은 세 방향으로 본다 (8.6). 수직으로는 완주를, 수평으로는 실행 통과를, 기준의 질로는 변이 검출을 본다.
        - 검증과 확인은 다르다 (8.4). 검증은 1~5단계의 검증기가 하고, 확인은 5~6단계의 실환경과 유저, 이탈로 하며, 그 결과는 `requirement`로 일반화한다.
        - 보고 5종 (8.24)은 검증 상태와 커버리지, 결함 분포, 가정 건전성, 독립성이고, 보고마다 리비전과 질의를 밝힌다.
        - 에이전트 V&V (8.25)에서 목표는 역할의 책임이다. 자극은 작업 집합과 요구, 의도된 이탈이다. 기준은 shape와 완주, 인지 누락률, 안전 정지다. 검증은 3단계 시뮬레이션 프로젝트를 중심으로 한다.
        - 사후 분석 (12.12)은 **기호 진단**(불만족 핵, 보간, 최약 전제조건, 명세 추론)에서 시작해 요인 추론, 지침, 어휘와 요구·기준·ODD 후보의 차례로 간다. 산출이 없으면 실패다. 보간 설명을 온톨로지 어휘로 쓰지 못하면 어휘가 모자란 것이다.
        - 선제적 V&V (8.27)의 트리거는 ODD 경계 근접과 커버리지 공백, 외부 지식 변화, 증거 노화다. 산출은 전부 `origin:observed` 후보다. 적응형 실행기는 테스트 케이스를 고르기만 하고, 테스트 케이스는 생성기가 만든다.
