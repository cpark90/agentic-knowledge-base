# Agentic Knowledge Base — 구조도

> 설계 노트 `agent-knowledge-system-notes.md`의 운용 지도. 괄호 번호는 노트의 절.

## 궁극 목적

- 특정 분야에서 사업을 수행하는 업체가, 그 분야의 지식을 에이전트가 활용할 수 있는 형태로 축적하고, 프로젝트마다 그 지식 위에서 시스템을 만들고 운용.
- **축적의 단위** (12.7)
    - 넘는 것: 온톨로지 어휘, 일반화로 올라간 제약(공리), ODD 코어, 결함 어휘, 교훈
    - 넘지 않는 것: **chunk.** 프로젝트 ODD 안에서만 유효
- **검증 대상 둘** (8.8) — 만들어지는 제품 / 만드는 에이전트
- **지식 베이스 둘** (8.1) — 개발 KB / V&V KB. 분리의 이유는 독립성, 연동의 이유는 완주
- 대상 지식
    - **시스템을 만들기 위한 지식 — 개발 KB** (계층 정제의 산출. 상세는 아래 development KB 블록)
        - 요구: `requirement` plane, **functional 수준 전용.** 자연어(EARS 권장), 이해관계자와 관심사 명시. 판정 = 합의 (5.1, 6.1)
        - 의도의 틀: ODD — 모든 요구가 서는 조건의 분모. 온톨로지의 프로젝트 뷰 = 선별 + 값 할당 + 폐쇄 (3.1)
        - 후보: `-space`. 변수·후보 링크·양립 제약. logical (9.4)
        - 결정: `decision` plane. 결론·근거·대안의 복합체. **어느 요구의 어느 관심사에 기여하는지 명시** (6.8)
        - 계약: `contract` plane. 인터페이스
        - 스키마: `schema` plane
        - 가정: 모든 항목이 서 있는 전제. ODD 조건 위의 명제 (6.5)
        - (합격 기준은 V&V KB로 이동 — 아래)
        - 역량 질문: 온톨로지가 답해야 하는 질문 목록 = 요구사항이자 완료 판정. CQ1~20 (2.7)
            - CQ19 "executable까지 닿지 않은 요구는" / CQ20 "요구로 거슬러 오르지 못하는 산출물은"
        - 구현: `artifact` plane, **executable 수준 전용** (6.1)
    - **검증·확인을 위한 지식 — V&V KB** (8.2, 상세는 아래 V&V KB 블록) — 코어의 두 번째 인스턴스. plane 실체만 다름
        - 검증 목표: `requirement`. 요구에서 `derives-from`
        - **시나리오**: `decision`. 자극(결론)·요인(근거)·배제 자극(대안). 변수는 ODD 속성
        - 합격 기준: `contract`. **logical 수준의 판정식.** verifier와 대상의 계약. 기준 없는 `verifies`는 거부
        - 케이스 형식: `schema`
        - 검증기: `artifact`, executable. **`verifies`의 유일한 주어는 V&V KB 청크**
        - 판정 주석: `annotation`. 결함 분류
    - **시스템에 대한 지식** (계층 일반화의 입력)
        - 관측: 실행 기록 `agt:Run`. V&V KB `memory`. concrete 전용, append-only. **시간은 여기와 `prov:wasRevisionOf`가 운반** (0.5)
        - 주석: `annotation` plane. 판정, 리뷰, 설명. 대상의 level을 물려받음 (6.4)
        - 기억: `memory` plane. 단기, 첫 실행 시 한 번에 읽음 (11.4)
        - 결함: 관측에서 추론된 실패. 3갈래 × ODC 유형 × 한정자 × 트리거 (11.1)
        - 교훈: 기억·관측에서 승격된 것. 개발 KB로는 **요구·결정·규칙**, V&V KB로는 **시나리오·기준** (6.3)
    - **순환**: 만들기 위한 지식 → 시스템 → 시스템에 대한 지식 → 교훈 → 만들기 위한 지식
        - 정제가 `refines`를, 일반화가 `prov:wasDerivedFrom`을 남김 — 순환 자체가 추적 가능
        - 일반화가 청크가 아니라 온톨로지까지 닿아야 함

## Agentic Knowledge Base

### methodology — 지식을 축적·운용하는 전체 순서와 그 이유

- 프로파일 구축 → 프로젝트 ODD 작성 → 정제(저작) ⇄ **V&V 파생** → 조회 → 연결 → 갱신 → 뷰 → 일반화 → (교훈이 다시 프로파일·ODD·요구·시나리오·결정으로)

| 단계 | 전제 | 완료 판정 |
|---|---|---|
| 프로파일 구축 | 코어 온톨로지 | 품질 검사 통과, 코어 수정 없음 (2.11) |
| ODD 작성 | 프로파일의 조건 어휘 | 5단계 절차 통과 (3.8) |
| 정제(저작) | ODD — 없으면 스코프·가정을 만들 수 없음 | 게이트 4종 통과, `refines` 연쇄가 functional까지 (6.8) |
| 조회 | 스코프 (ODD × 카탈로그) | 작업 집합이 컨텍스트 예산 안 (1.4) |
| 연결 | 하네스의 읽기·쓰기 기록 | 링크 밀도 하한, 구축 비율 (10.14) |
| 갱신 | 가정 판정식 A~B등급 | 전수조사 없이 무효 범위 계산 (6.10) |
| 뷰 | 링크·복합체 | 질의로만 생성, 사본 없음 (4.6) |
| V&V 파생 | 개발 KB의 요구·범위·구현 | 각 높이의 검증 대응물 존재 — 목표·기준·검증기 (8.3) |
| 일반화 | 실행 기록 누적 | 온톨로지 확장 건수 > 0, 사후분석마다 산출 (12.12) |

- 도입 순서와의 구분: methodology는 운용의 순환, 도입 순서는 체계를 세우는 8단계 (Part XIV, 단계별 작업·통과 조건은 14.1) — 1~6 개발 KB, 7 V&V KB, 8 복원·감사. 사례 프로젝트 하나에서 끝까지 (부록 B). 도입 1단계만으로 이득이 없으면 중단

### input — 체계가 소모하는 파라미터 (Part XI)

- 도메인 프로파일 · 에이전트 카탈로그 · 실행 모드 · 메모리 승격 규칙 · 재검증 시점 · 태그 어휘 · 판정 도구 바인딩 · 앵커 해석기 · 청크 상한 · 일반화 임계값 · 커버리지 임계 · 후보 상한
- 전부 온톨로지 어휘로, 버전 관리. 입력 간 의존 순서 있음 (11.7)

### result

result는 코어(공통)과 그 위의 두 지식 베이스로 이루어진다. ontology·tools·rules·method 각각을 **코어 / development / V&V** 세 층으로 적는다.

#### 두 지식 베이스의 정의

| | development KB (Part VII) | V&V KB (Part VIII) |
|---|---|---|
| 목적 | 요구사항 명세로부터 실질적 산출물을 생산하기 위한 지식 | 요구·산출물 전 과정에 연동되어 시나리오 기반 검증·확인을 수행하는 지식 |
| 계층 | 요구 → 형식화 → 범위·제약 → 값 → 구현 | 검증 목표 → 시나리오 형식화 → 논리 시나리오+기준 → 케이스 → 검증기 |
| 완료 판정 | 정제 완주·후방 추적 귀속 100% + 계약 선행 + 대안 기록 + 가정 valid + **V&V `verifies` valid** (7.9) | 목표 파생·기준 바인딩·V&V 완주 100% + 변이 검출 + 독립성 0건 (8.26) |
| 편집 주체 | design · developer · orchestrator | V&V engineer · 검증기 저자 · executor · judge |
| 상대 KB 접근 | V&V KB **읽기만** | 개발 KB 읽기 + `verifies`로 참조 |
| 지표 | 전방 추적 커버리지 · 후방 추적 커버리지 · 결정 완결률 · `-space` 체류 · 계약 선행률 · 대안 기록률 (7.8) | 목표 파생률 · 기준 바인딩률 · V&V 완주율 · 실행 통과율 · 변이 검출률 · 재현 실패율 · 검증 대응물 지연 (8.26) |

- **ontology** — 지식의 코어 및 뼈대
    - 코어 (공통)
        - 분야 무관. plane·level·조건·가정·역할 + 청크·복합체·링크 타입
        - 상위 온톨로지(BFO/IAO) 위에 구축. 최상위 분류를 지어내지 않음 (2.2)
        - 모듈: `entity/`(plane별) · `related/`(횡단: 조건·스코프·가정·workset·revision·trace·하네스) · `vv/` · `profile/` · `defect` · `defect-rules` (2.3)
        - 어휘와 형식화 분리 — `defect`는 분류만, `defect-rules`는 추론 규칙
        - **온톨로지 온톨로지 검사 3단계** (2.5): report(구문·스타일) / verify(SPARQL 안티패턴 — 게이트 대부분이 여기) / reason(불만족·의도치 않은 동치). 빌드 시스템이 컴파일러
        - 용어 제안 워크플로 (2.5): 에이전트 template 행 → 3계층 → 유저 승인 → 확장 모듈. 에이전트 = 신뢰할 수 없는 센서
        - 사례 교훈 (2.12): 코어는 수십 클래스로 충분 · 게이트는 질의로 · `sources` 빈 청크 = 실패 · 신뢰 등급 전파 · 판정 이력을 head에
        - 관계는 RO 하위 속성으로 (2.8). 추론은 OWL 2 RL 안에서 (2.9). 시간 정체성: IRI 지속 + `prov:wasRevisionOf` (2.6)
        - 분야 프로파일: 코어를 **확장만** 하는 모듈 `profile/<분야>` (2.11, 부록 D)
    - development
        - `entity/` 일곱 plane의 개발 실체 (7.2): `RequirementChunk`(EARS 패턴·이해관계자·관심사 필드) · `DecisionChunk`(역할 태그 결론/근거/대안, `serves`) · `ContractChunk`(시그니처, 사전·사후조건) · `SchemaChunk`(호환 관계) · `ArtifactChunk`(구현, 앵커) · `AnnotationChunk` · `MemoryChunk`
        - 개발 어휘: EARS 다섯 패턴, 관심사 분류, 계약 호환성(하위 호환/비호환), 표본 추출 근거 유형
        - 역량 질문 중 개발 KB 소관: CQ1 충족 · CQ3 배제 대안 · CQ4 무효 범위 · CQ7 고아 · CQ16 할당 · **CQ19 정제 완주** · **CQ20 후방 추적 귀속** (2.7)
    - V&V
        - `vv/` 모듈 — 일곱 plane의 V&V 실체 (8.2): 검증 목표 · **시나리오**(자극·요인·배제 자극) · 합격 기준(판정식) · 케이스 형식 · 검증기 · 판정 주석 · 실행 기록
        - 위험 분석 산출 (8.21): 현상(ODD 조건 + `defect` 요인) · 인과(`defect-rules`) · 지표 · **시나리오 부류 abstract 라이브러리**(프로젝트를 넘어 재사용) · 목표 거동(Runbook)
        - 시나리오 도메인 모델: actor(에이전트·유저·서비스)·action — OpenSCENARIO DSL 구조에 자체 도메인 (부록 E)
        - 결함 어휘: 3갈래 × ODC 유형 × 한정자 × 트리거 × 발견 단계 (8.16~8.18)
        - 역량 질문 중 V&V KB 소관: CQ5 작업 집합 · CQ6 ODD 안팎 · CQ10 결함 요인 · **CQ11 무엇을 검증하는가** · CQ17 양립 후보
- **tools** — ontology·method·rules를 수행·관리하는 도구
    - 검사 (코어, rules의 기계 형태)
        - `validate` — 3계층: `report` · `verify`(SPARQL 안티패턴·TIM·정의역치역) · `reason` (2.5, 4.4, 10.1)
        - `term_propose` — ROBOT template 행 생성·검사·승인 큐 (2.5)
        - `chunk_lint` — 42줄·라벨·plane·level 유일성·수준 허용표 (4.4, 6.4)
        - `chunk2kg` — head·provenance·pubinfo 추출, 엔티티 검증, 내용 해시 (4.3, 2.12)
        - `canonicalize` — 정규화 직렬화. 전체 그래프의 리비전 해시 (2.5, 0.5)
        - `odd_check` — COD 대조, 이탈 감지 (3.5)
        - `assume_check` — 가정 판정식 실행 (6.9)
    - 활용 (코어, method의 기계 형태)
        - `workset` / `labels` — 스코프 × level 창 → 작업 집합 (0.5, 5.6)
        - `link` — 구축 기록→후보, 복원 파이프라인 (10.3, 10.4)
        - `propagate` — 무효화 전파 8단계 (6.10)
        - `revalidate` — 재판정 큐, 규칙 카탈로그 8종 (10.11)
        - `query` — CQ1~20 (2.7, 10.13)
        - `impact` — 변경 전 의존 집합·승인 필요 수 (12.6)
        - `project` — tangle·weave·매트릭스·보고. 저장하지 않고 질의 (4.6, 12.10)
        - `metrics` — 코어 지표: 고아율·링크 밀도·suspect 비율·누락률·라벨 대표성 (4.13, 10.14)
    - development
        - `gate` — 전이 게이트 4종 검사: 기여 명시 / 범위·제약 / 표본 근거 / 기준 바인딩 (6.8). 전 게이트 총람과 실행 계층(shape·verify·analysis·test·human)은 6.7
        - `space_check` — `-space` 호 일관성·ODD 경계·`when` 평가·증거 기록 규칙 적용·확정 제안 (9.6, 9.10, 9.11)
        - `feedback` — `-space` → 체크박스 파일 생성 · 되읽기 → 확정 (12.2, 13.5)
        - `contract_check` — 계약 선행, 타입, 사후조건 CEL 실행 가능성 (7.5)
        - `schema_compat` — 하위 호환 판정, 비호환 시 새 IRI + `supersedes` (7.6)
        - `adr` — 결정 복합체 뷰 (7.4)
        - `tangle` — 구현 청크 → 코드 파일 (4.6)
        - `dev_metrics` — 전방 추적 커버리지·후방 추적 커버리지·결정 완결률·`-space` 체류·계약 선행률·대안 기록률 (7.8)
    - V&V
        - `goal_derive` — 요구 → 검증 목표 후보 (8.19)
        - `scenario_lint` — 변수가 ODD 속성인가, 부류 참조, 배제 자극 존재, 자극≠기준 (8.22)
        - `case_gen` — `keep(범위)` + `cover()` → concrete 케이스. 규칙(등가·경계·조합·요인·관측)과 seed를 provenance에 (8.23)
        - `verifier_bind` — 기준 바인딩 검사. 기준 없는 `verifies` 거부 (8.11)
        - `env_assign` — 결함 요인 → 환경 단계, 재현성 조건 (8.10, 8.12)
        - `run` — 실행기. 리비전·seed·환경 버전 기록, 실행 기록 append (8.15)
        - `judge` — 판정. 학습된 판정자면 3지표 검사, 결과를 head `verified` 목록에 (8.14, 2.12)
        - `mutate` — 변이 주입 표본 검사 (8.6)
        - `coverage` — 정제 완주·후방 추적 귀속·logical 공간 커버, 경계값 별도, 6단계 제외 (8.7)
        - `defect_classify` — `defect-rules` 추론: 요인·한정자·트리거·발견 단계 (8.16~8.18)
        - `sim_trust` — 시뮬레이션 신뢰도 요인별 상관 (8.13)
        - `vv_report` — 검증 상태·커버리지·결함·가정 건전성·독립성 (8.24)
        - `independence_audit` — 개발 역할의 V&V KB 쓰기 흔적 = 0 (8.5)

- **rules** — 지식의 모델링을 위한 규칙
    - 코어 (공통)
        - chunk: 42줄 · 한 plane·level·주제·파일 · 4분 이름 그래프 · IRI = uuid+해시 · 라벨이 인터페이스 · 상태 기계 · 분할·병합 (4.1~4.11)
        - 복합체: `part-of`, 같은 plane·level만 · 7±2 · `co:List` · 참조 재사용 · 상태 집계 (4.5)
        - plane: 판정 방식으로 정의 · 코어 일곱 · 단방향 영향 규칙 · 추가 기준 (5.1~5.5)
        - level: 요구→산출물 정제 수준 · 다섯 수준의 거주 plane · 거주 밖 = shape 위반 (6.1, 6.4)
        - traceability: TIM · 링크 타입 12종 · `assumes`만 plane 횡단 · 구축 우선 · 후보→확정 · 본문 밖 · 상태 · 매트릭스 (10.1~10.12)
        - **후보의 구조** (9.10, 9.11): 수치 없음. 모든 링크에 `when` 조건(ODD·가정 위 CEL) — `assumes`·스코프 conditional의 일반형, 상태는 조건 평가 결과. 후보에 **증거 기록**(종류 6 × 극성 ±). 상태 전이는 증거 기록 규칙 — 구축/실행(+) 없이 확정 불가, 실행(−)은 즉시 기각, ±공존은 유저 큐. 언어모델은 제안·선호만
        - knowledge graph: ODD(뷰·분모·판정 필수·시간 제약 어휘·이탈=신호) · 리비전·작업 집합 · 시간열 개체 없음 · 가정은 ODD 위 · 통제 어휘 · 태그 (Part III, 0.5)
    - development (7.2~7.7)
        - `requirement`는 functional 전용, EARS 패턴·이해관계자·관심사 필수
        - 결정은 항상 결론·근거·대안 세 청크의 복합체. **대안 청크 없는 결정 = shape 위반.** "대안 없었음"도 기록
        - 결정은 수준마다 별개 청크, `refines`로 연결. concrete 청크가 생겨야 확정
        - **계약 우선** — `contract` abstract가 구현보다 먼저. 계약 없는 구현 = 정제 단절
        - 스키마는 `decision`에서 `derives-from`, `contract`를 `constrains`. 비호환 변경 = 새 IRI + `supersedes`
        - `artifact`는 구현만. verifier는 V&V KB
        - developer는 concrete 결정과 확정 스키마 없이 구현 불가 (스코프 conditional). developer 작업 집합에 `-space` 없음
        - 결정 대체는 `supersedes`. 옛 결정은 deprecated, 그 `satisfies` 전부 suspect
        - 완료는 V&V KB의 `verifies` valid를 읽어야 선언 가능
    - V&V (8.2~8.5, 8.11~8.15)
        - **독립성**: 개발 역할은 V&V KB 쓰기 불가. 기준 수정은 요구 수정으로만. 저장 분리, V&V → 개발 단방향 의존
        - **검증 대응물 필수**: f→a에 검증 목표 / l→c에 합격 기준 / c→e에 검증기. 없으면 개발 게이트 실패
        - `verifies`만 KB를 가로지름. 방향은 V&V → 개발, 같은 level끼리
        - 시나리오 = `decision`(vv) 복합체: 자극·요인·배제 자극. 변수는 ODD 속성만. ODD 밖 자극은 `odd:outside`, 커버리지 제외
        - **기준 ≠ 자극**: 기준은 `contract`(vv) 별도 청크, `verifies` 속성으로 바인딩. 판정식 없는 기준은 abstract로 강등
        - concrete 케이스는 사람이 쓰지 않음 — `keep`+`cover`에서 생성. 표본 근거 없는 케이스 거부
        - 검증기 저자 ≠ V&V engineer (또는 다른 세션)
        - 재현 불가 → 5~6단계 강등. 6단계 관측은 커버리지에 넣지 않음
        - 학습된 판정자는 선택·판별·캘리브레이션 3지표 통과 + 사람 승인. 판정 결과는 head `verified` 목록에 누적
        - 시뮬레이션 신뢰도는 요인별. 상관 미검증 요인의 3단계 통과는 커버리지에 넣지 않음
        - 확인 결과의 목적지는 `requirement` — 요구가 바뀌는 유일한 정규 경로
        - **불일치의 귀속은 결정** (8.4): 산출물 / 지식(요구 과도·제약 부족·가정 누락) / 둘 다. V&V `decision`의 **지침**(귀속·조치·배제된 전략). 진단은 기호 도구 먼저
        - 검증기 결과는 개발 KB `satisfies` 후보의 증거 기록에 (+)(−)로 흘러감 — 링크가 아니라 증거 기록 항목이라 방향 규칙 유지 (9.11)
