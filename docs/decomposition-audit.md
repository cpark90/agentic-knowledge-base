
# 분해·승격 감사 — 지식은 어디서 왔고 원본은 어떻게 되었는가

이 저장소의 결정은 세 경로로 들어왔다. 이 문서는 그 경로들의 **커버리지 감사**다.
원본의 구조 요소를 하나씩 어디로 갔는지 대응시키고, 옮기지 않은 것은 명시적 사유를
남긴다.

| 경로 | 원본 | 결과 | 원본의 운명 |
|---|---|---|---|
| **분해** (2026-09-01, §1) | 설계 노트 v1 (2,476줄) | 결정 115개 + `docs/` 문서 5개 | 제거되었다가 **v3로 복귀** (§3) |
| **승격** (2026-09-01~02, §2) | 참조 저장소 `harness-functional` · `harness-concrete`의 설계 문서 | 결정 (§2) | **유지** — 일반 원칙만 옮기고 운영 명세는 그대로 두며, 이송 표기를 남긴다 |
| **v3 재도출** (2026-09-10, §3) | 설계 노트 **v3** (2,789줄, [`agent-knowledge-system-notes.md`](agent-knowledge-system-notes.md)) | 요구 26 + 결정 145 (`kb/dev/`) | **유지** — 살아 있는 설계 원본이다. 노트 유래 옛 결정 126개는 deprecated이다 |

두 경로의 차이가 중요하다. **분해**는 원본이 이 체계의 것이었으므로 옮기고
지웠다. **승격**은 원본이 다른 프로젝트의 운영 문서이므로, 일반 지식만 가져오고
그 프로젝트가 계속 쓸 부분은 남긴다.

감사의 방향은 [`id:chunk-d0015`](../chunks/decision/d-0015-composition-workflow.md)가
정한 것과 같다. 방향은 **원본 → 표현**이다. 게이트가 초록이어도 반영이 완료된 것은 아니며,
소스의 구조 요소를 빠짐없이 열거해 각각을 매핑해야 done이다.

# 1. 분해 — 설계 노트

v1 분해의 절별 대응표(노트 절 → d-0021~d-0155)는 그 결정들이 v3 재도출로 deprecated 되어 역사 기록이다.
원문은 git 이력(`git log -- docs/decomposition-audit.md`, 2026-09-13 이전 판)에 있다.

## 무엇이 어디로 갔는가 — 세 갈래

| 원본의 성격 | 목적지 | 이유 |
|---|---|---|
| `[확정]` 규칙 | **결정** (`chunks/decision/`) | 결론·근거·대안을 가진 지식. plane=decision, level=concrete |
| 진행 상태·추적 대상 | **설계 문서** (`docs/`) | 결정이 아니라 변하는 상태다. 항목으로 만들면 계속 무효화된다 |
| `[?]` 미해결 | [`open-questions.md`](open-questions.md) | 결론이 없으므로 결정이 될 수 없다 |

대안이 남은 항목인 `[안]`은 해당 결정의 **대안** 절에 "미확정"으로 적었다.

## 원본을 다시 보려면

```bash
git log --all --oneline -- agent-knowledge-system-notes.md
git show ed633cc:agent-knowledge-system-notes.md
```

기계가 읽는 출처는 각 항목의 `derived_from: [.../id/doc-system-notes]`이고, 그
개체는 `kg/base-kg.ttl`에 있다. 문서가 사라져도 IRI는 유지된다(지속 IRI, 0.7절).
본문의 `(노트 N.N절)` 인용이 절 수준의 출처 기록이다.

# 2. 승격 — 참조 저장소의 설계 문서

1차(2026-09-01, d-0013~d-0020)·2차(2026-09-02, d-0156~d-0163·d-0176~d-0185) 승격 목록과 저장소 사이 이관은
git 이력에 있다. 승격된 결정은 `chunks/decision/`에 살아 있고 `sources`가 원천을 가리킨다.

1,388줄의 `harness-functional`과 1,171줄의 `harness-concrete`의 설계 문서를 같은
규칙으로 훑었다. **분해와 달리 원본은 남는다.** 그 저장소들이 계속 쓰는 운영
문서이기 때문이다. 일반 원칙만 가져오고 구체 술어·경로·명령·실측치는 그대로
두며, 원본에는 이송 표기를 남긴다.

## 승격의 판정 기준

**"이 규칙이 harness 프로젝트가 아니어도, 온톨로지로 지식을 관리하는 다른
프로젝트에서 참일까?"** 참이면 일반 지식이다. `ho:` 클래스·프로퍼티 이름에
묶인 규칙, 디렉토리 배치, 도구 CLI, 파일 경로, 레시피 실측치는 전부 유지다.

**과승격은 베이스를 오염시킨다.** 두 저장소에 할당한 IRI 범위는 각 20개였고
실제로 쓴 것은 8개와 10개다. 애매한 것은 승격하지 않았다.

## 승격하지 않고 유지한 것 — 판단의 근거

| 후보 | 판정 | 이유 |
|---|---|---|
| `ONTOLOGYSTYLE` §1a·1b·1c (anti-orphan/drift/rot) | 유지 | **이미 d-0014·d-0013·d-0016**에 있다. 원본이 이미 그 청크를 가리킨다 |
| `HARNESS-ODD.md` 전체 | 유지 | 베이스 ODD 규칙(d-0008·d-0058~d-0066)의 **인스턴스**이지 규칙이 아니다 |
| `coverage-gap-channels.md` | 유지 | d-0015가 이미 "어휘 범주가 없으면 스키마 확장을 트리거"를 담는다 |
| `RECIPE_STANDARD` §0 "실측 교집합이 표준" | 유지 | d-0019 근거에 이미 있다 |
| BIND의 "후보 집합으로 미확정 표현" | 유지 | d-0096~d-0104가 이미 다룬다. 그 **위에 얹히는** 실질만 승격했다 |
| executable / structural 판정 메커니즘 구분 | 유지 | d-0064(판정 방법 등급)가 비용 축을 이미 다룬다 |
| `ho:` 술어 목록·프레디킷 순서·Turtle 포맷·디렉토리 배치 | 유지 | 어휘 이름에 묶인 운영 규약 |

## 감사가 잡아낸 것

- **`materialize-design.md`의 시점 오류.** 이 문서는 concrete에서 작성된 채
  functional로 옮겨져 "this repo"가 concrete을 가리키고 상대 링크 셋이 전부
  깨져 있었다. 이관이 만든 결함이며, 이관 규칙을 지켜도 **경로 표현은 따로
  고쳐야 한다**는 사례다.
- **d-0019의 실측치가 낡아 있었다.** "53개 레시피의 실측 교집합"이라고 적혀
  있었으나 원본은 2026-09에 58개로 재실측되었다. 승격된 청크는 원본이 갱신되면
  같이 낡는다. 실측치를 청크에 넣을 때는 시점을 함께 적어야 한다.

# 3. v3 재도출 — 노트의 복귀와 전면 재도출 (2026-09-10)

파트별 에이전트 할당과 산출 표는 git 이력에 있다. 재도출 결과는 `kb/dev/`가 원본이고, 노트 절과 결정의 대응은
`sources`·`metrics`의 확정 문장 커버리지가 잰다.

노트가 2,789줄의 v3로 갱신되어 돌아왔고, 유저 승인
([`feedback/design-detail-review.md`](feedback/design-detail-review.md), 반영 범위 A)에
따라 `[확정]`을 전면 재도출했다. §1의 분해와 달리 **원본을 지우지 않는다.** 노트는
살아 있는 설계 원본으로 `docs/`에 남고, 재도출된 결정이 그것을 `derived_from`으로
가리킨다.

## 무엇이 어디로 갔는가

| 원본의 성격 | 목적지 |
|---|---|
| 이해관계자 관심사 | **요구 33건** (`kb/dev/requirement/`, EARS, functional; v3 26 + 공백 보충 7) + [`../INTENT.md`](../INTENT.md) |
| `[확정]` | **결정 188건** (`kb/dev/decision/<파트>-<슬러그>/`, 결론·근거·대안 세 청크 복합체; v3 145 + v4·v5 델타 37 + 2026-09-11~12 추가 4) |
| `[안]` | 해당 결정의 `alternatives.md`에 "미확정" 표기 |
| `[?]` · Part XVII | [`open-questions.md`](open-questions.md) (30건 + 이 저장소 관찰) |
| Part XIV 도입 순서 | [`roadmap.md`](roadmap.md) 도입 8단계 |
| 코어 어휘 신설분 | `kb/ontology/` — state·tag·시간 제약·수준 허용표·RequirementChunk·링크 확장·contentHash |

## 재도출이 잡아낸 것

- **노트 v3 내부의 v1 잔재**: 0.4절 스코프 예시가 v1 plane인 `source`·`interface`·
  `protocol`을 쓰고, "Part VII/VI/XIV" 참조 몇 곳이 재번호 전 기준이며, 5.3절이
  "현재 6개"라 하나 plane은 7개다. 유저 판정 대상이다.
- **요구 층의 공백**: 컨텍스트 예산, 명명·표기 결정론, 입력의 명시·버전 관리,
  "문서는 생성한다", 검증 수단 자체의 신뢰도, 감사 자족성, 재현성("공백 세션에서
  같은 산출물")에 해당하는 요구가 26건에 없다. 여러 결정이 refines를 차선으로
  걸었다. 요구 층 확장 후보다.
- **내용이 뒤집힌 대체 2건**: d-0084(전 plane 5단 격자)→성긴 수준 허용표,
  d-0005(추상화 계층)→정제 계층이다. 배제 사유가 새 결정의 alternatives에 있다.
- **복합체 동질성과의 긴장**: 결론 concrete + 근거 logical인 결정 복합체는 4.5절
  동질성 규칙과 충돌한다. [`open-questions.md`](open-questions.md)에 등록했다.

# 이 감사의 한계

- **의미 보존은 기계가 검사하지 않는다.** 절이 청크로 매핑되었다는 것과 그
  청크가 원본의 뜻을 정확히 옮겼다는 것은 다르다. 절별 대응표는 전자만
  보증한다.
- 표·예시·다이어그램은 42줄 안에서 **압축**되었다. 원본의 표 전체가
  필요하면 git 이력을 본다.
- 분해는 다섯 에이전트가, 승격은 두 에이전트가 병렬로 수행했다. 인접한 절이
  다른 에이전트에게 할당된 경계에서 중복이나 누락이 생길 위험이 있어, 통합 시
  라벨 목록을 훑어 중복을 확인했다.
- **승격된 항목은 원본이 바뀌면 낡는다.** 원본이 살아 있는 운영 문서이기
  때문이다. 이것이 분해와 다른 점이다. 실측치·수치가 들어간 항목은 시점을 함께 적었고,
  원본의 이송 표기가 역방향 포인터 역할을 한다.
